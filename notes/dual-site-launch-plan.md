# 简幕重构与双站首发方案

2026年11月5日更新。

本文写首发怎么做：分几个阶段，每个阶段依赖什么、交付什么、做到哪里算完成；新仓库怎么公开；权限、数据披露和平台条款怎么处理；验证和提交商店要满足哪些条件；首发后怎么迭代。产品是什么、首发和各次更新含哪些功能、每项做到哪里算完成，见[产品需求说明（PRD）](product-prd.md)。代码怎么组织、每一步的技术退出条件，见[架构设计](architecture.md)。同一件事只在一处详写，本文碰到功能细节和代码结构只给链接。

状态标注沿用 PRD 第 5.1 节：当前已实现、首发待实现、首发待验证、更新一到三、候选、不做。本文不预填实验结果，不承诺上架日期或工期。

## 1. 已确定的方向

1. 目的排序：自用第一，开发者本人的公开作品第二，公开用户第三。不追求增长，不做变现。成功标准见 PRD 第 2 节。
2. 主线：帮用户几分钟内判断一个长视频值不值得看、重点看哪段。
3. B 站和 YouTube 同时首发，不先单发 B 站。YouTube 在真实页面验证通过后才提交商店。
4. 首发以 Chrome 应用商店为目标，Edge 不是前提。
5. 重构放在首发之前，和双站改造（站点适配层、统一视频身份）一起做。不再与 Digest for Bilibili 同步；内部名字、代码结构、界面和图标、提示词全部换成简幕自己的。
6. 新代码写在新建的公开仓库 `jianmu` 里，改用 TypeScript 加一个轻量构建步骤，选型和理由见架构设计第 2 节。B 站的读取实现（含请求签名）例外：独立评估完成前不进公开仓库（第 4.4 节）。现有仓库保持私有，作为存档；现有的 PR 记录留在那里。
7. 不写自动迁移代码。商店版是一个全新的扩展，开发者本人的资料靠备份导出、导入搬过去，所以新版要能读旧格式的备份。
8. 不赶日期，越快越好。公开新仓库不等于提交商店，上线时间看审核。
9. 首发后小步更新，按更新一、二、三的顺序。
10. 形态不变：没有开发者后端，用户自带模型 API 密钥，资料存在本机。

本文取代此前版本里的三处做法：保留沿用自 Digest for Bilibili 的内部标识；在原仓库里小步改造、不整体重写；先让 B 站跑通新结构，再开始接 YouTube 的串行顺序（现在后台服务搭好后两边并行，见第 4 节）。

## 2. 当前事实与缺口

### 2.1 现有版本

- 只支持 B 站。发布代码约 2.6 万行，按行追溯约四成来自 Digest for Bilibili。侧边栏一个文件 4500 多行，近一半是 Digest for Bilibili 的代码。播放页卡片和稍后再看粗筛页是本项目从零写的。
- 仍和 Digest for Bilibili 一样的：4 个图标；概览、划词解释、笔记润色三份提示词；侧边栏「字幕、概览、笔记、问答」四个页签；商店的扩展描述。三套主题是本项目加的。
- 视频身份写死成「BV 号加分 P」，散在缓存键、任务键和界面状态里，七百多处。内部标识沿用 Digest for Bilibili 的命名：27 个全局对象、7 个存储键和 IndexedDB 库名。
- 现有测试全部通过。约一半靠在隔离环境里整份运行页面或后台脚本，和现有文件布局绑死，搬不进新结构；其中不少是防 Digest for Bilibili 旧功能回来的回归测试。测试数量和旧测试的去向见架构设计第 4.4 节。
- 「回收不用的主机权限」从来没成功过：一次回收里混进了必需权限，整批被浏览器拒绝，错误又被吞掉（在 Chrome for Testing 里实测；正式版 Chrome 用同一套代码，推断一致，阶段七实机再核对一次）。现有隐私政策和商店稿里「换了地址再保存，旧地址的权限会收回」现在不成立。
- 数据同意是一个全局版本号，现为 2，严格相等才放行。界面分不出「从没同意过」和「说明更新了」。
- 国内快捷预设的默认模型名是服务商列出的旧名：服务商说旧名仍然接受，但对应的旧模型已经退役，请求改由新模型处理。

### 2.2 YouTube 和画面截取

- YouTube 只有一个实验分支。它的单元测试和本机模拟自测都通过，但从没在真实页面上得到结果。YouTube 读取字幕首发待验证。
- 画面截取只有规范和浏览器源码层面的推断：在内容脚本里把页面上的视频画到画布上，普通视频应当不用新权限；从侧边栏点按钮拿不到浏览器可见区域截图的权限。都没在真实页面上验证。

### 2.3 商店、名称和平台

- 还没有 Chrome 应用商店开发者账号。官方说多数扩展几天内审完，也可能要几周；新开发者、新扩展可能审得更久。
- 隐私政策没有公开地址。现有隐私政策写着「尚未发布的开发版」、没有联系方式，还写了 B 站接口签名的细节；商店稿里隐私政策和反馈链接还是占位。两份首发都要重写。
- 图标和商店简短说明仍是 Digest for Bilibili 的。旧实机检查清单约一半的步骤没跑过。
- 「简幕」初查没有同名产品，还没查过官方商标库。开发者本人账号下的 `jianmu` 仓库名可用；GitHub 上另有同名但不同类的项目（例如 DevOps 工具「建木」），搜索时会混在一起。
- 两站的条款都限制未经许可用自动方式获取内容，都没有专门讲浏览器扩展的条款；YouTube 服务条款另外限制复制、下载内容和规避限制。各条的内容和简幕要满足的条件见第 8 节。
- 2026 年有与 B 站相关的开源项目在收到法律函件后关停或停更。函件是权利方的主张，不是判决，但说明平台会对这类项目采取行动。
- 没有使用数据。产品判断依据的是开发者本人的使用习惯（PRD 第 3 节）。

## 3. 首发范围

首发包含什么以 PRD 第 5.2 节为准，这里只概括：

- 重写：内部名字、代码结构、界面和图标、提示词。
- 两站跑通现有功能；B 站专属的官方材料、播放页卡片、稍后再看粗筛保留；本窗口全部生成覆盖 YouTube 标签页。B 站的自动读取能不能留在公开仓库和商店包里，取决于第 4.4 节的独立评估；评估做不成时是否接受「公开版暂不自动读 B 站字幕」，由开发者本人决定（第 12 节）。这是首发的阻断项，决定之前不改首发范围。
- 首次启用确认（PRD F22）；速览、精读两种模式和自动切换；悬停才出现的笔记图标；每个功能单独调推理强度；自动生成总开关（默认关），打开后打开视频就生成概览。
- 解释当前画面：首发待验证。阶段一的画面判定表全部通过，表示可以进入实现；构建开关打开前，实现还要满足 PRD F11 的完成标准和用法一的拒绝条件（第 4.1 节）。实验不通过时，首发移除全部画面功能，不拖首发；「解释当前画面」最早在更新一重新评估，画面信息并入概览、笔记里插关键画面仍按原计划和各自的前提推进，不承诺更新一全部上线。
- 发布必需的工作：隐私政策、截图、商店文案、商标检索、平台条款说明（第 8 节）。

支持范围：YouTube 首批只支持桌面普通观看页上已有字幕的视频；B 站保留现有范围，含分 P（PRD F01）。首发不做的见 PRD 第 5.3、5.4 节，首发后的更新见本文第 10 节。

## 4. 分阶段实施

| 阶段 | 内容 | 依赖 | 对应架构设计第 12 节 |
| --- | --- | --- | --- |
| 一 | YouTube 字幕和画面截取的可行性实验 | 实验扩展的改动和操作步骤（架构设计第 12 节第 2 步）；开发者本人提供样本链接 | 和第 1–3 步并行 |
| 二 | 新仓库与工具链，检查通过后公开 | 无 | 第 1 步 |
| 三 | 核心层移植 | 阶段二；移植前的对照准备 | 第 2–5 步 |
| 四 | 站点适配与双站 | 阶段三；YouTube 部分另要阶段一的字幕结论；B 站读取实现进公开仓库另要独立评估 | 第 6、7、10 步 |
| 五 | 界面与模式 | 阶段四的后台服务；解释当前画面另要阶段一的画面结论 | 第 8、9、11 步 |
| 六 | 发布准备 | 可以提前起草；定稿要等阶段五切换日用 | 第 12 步的材料部分 |
| 七 | 双站回归与提交 | 阶段四、五、六 | 第 12 步的检查部分 |

总规则：

- 一个 PR 只改一件事：移植、改身份、改行为、加功能各自成 PR。移植 PR 的黄金样本必须一致，改行为的 PR 逐条写明差异（架构设计第 3 节）。
- 每个阶段的退出条件全部满足才算完成。逐步的技术退出条件以架构设计第 12 节为准，本文写阶段层面的条件。
- 开发者本人日用的现有扩展在阶段五切换之前一直不动，出问题随时可以退回。
- 每批交付写清改了什么、为什么、检查结果、当前限制和下一个阻断项。不给工期。

### 4.1 阶段一：YouTube 字幕和画面截取的可行性实验

要回答两件事：YouTube 上有没有一种普通用户能用、不规避平台限制的方式读取已有字幕；在页面里截取当前画面能不能稳定拿到正确的帧。

做法：

- 用一个独立的实验扩展，不进新仓库，也不并进产品代码。字幕和画面合成一轮：同一次加载、同一次授权、同一批标签页、同一次导出。画面失败不影响字幕结果，两部分分开记。
- 在开发者本人的 Chrome 里跑，两站都登录；另开无痕窗口作未登录对照。
- 实验扩展的改动和操作步骤事先写好，放在私有存档里。遇到限流或人机验证提示立即停下整轮。
- 样本：约 12 个开发者本人常看的 YouTube 视频，类别可以重叠，至少覆盖拿信息的英文长视频、学英语的视频（播客、vlog）、一小时以上、只有自动字幕、有人工英文字幕、有中文人工字幕、多语言轨、多音轨、完全没有字幕、画面里有幻灯片代码或图表。B 站另选几个：知识区幻灯片、代码教程、分 P、番剧或电影各至少一个，只跑画面部分。不用这个小样本推断全站成功率。
- 存放：实验报告和原始结果属于接口分析材料，脱敏后只留在私有存档；截图只留在本机，不进任何仓库。公开文档只写按能力描述的结论。

字幕部分要记录：

- 每个视频：播放器字幕菜单里实际有哪些轨（作为「有没有字幕」的标准答案），音频语言，有没有多音轨。
- 每种读取方式：能不能拿到正文，时间轴和视频对不对得上，覆盖多少，失败归到哪一类。
- 已登录的普通窗口和未登录的无痕窗口有什么差别。
- 站内连续换视频、快速切换、前进后退、扩展晚于页面加载时，读到的是不是当前视频的数据。
- 频道编号和简介能不能读到（按频道记住模式和提示词要用）。
- 两站播放器控制栏出现、隐藏时有没有可用的页面信号；`n` 键在 YouTube 上会不会冲突；播广告时页面的表现。
- 在侧边栏里点「在 YouTube 上启用」能不能直接弹出浏览器的授权框。
- 当时开着的其他扩展；有没有出现「确认你不是机器人」之类的提示；播放器状态有没有被改动。

画面部分的判定（任一项不通过，按第 3 节的退路：首发移除全部画面功能）。这里判断的是截帧能不能做，不是某一家模型能不能看图；全部通过只表示可以进入实现，不等于可以发布：

| # | 测什么 | 通过标准 |
| --- | --- | --- |
| 1 | 找到主视频 | 两站普通样本都能唯一找到主视频元素。遇到 B 站的特殊播放器元素单独记下，另测能否取到画面 |
| 2 | 读得出像素 | 普通样本（不含番剧、电影、付费内容）全部不报安全错误 |
| 3 | 不是黑帧或空帧 | 暂停在非黑场画面时，截图和屏幕所见一致，平均亮度高于 8/255 |
| 4 | 是当前这一帧 | 暂停时和屏幕一致；播放中截到的帧和点击时的播放位置相差不超过 0.2 秒 |
| 5 | 在扩展里结果一样 | 内容脚本里和页面自己的环境里各跑一遍，结果一致 |
| 6 | 模型读得出字 | 5 个幻灯片或代码样本，按实际播放清晰度截图，长边缩到 1456、JPEG 质量 0.85。至少海外预设的一个能看图的模型逐字读对标题和至少 3 行正文或代码；读不对时换更大尺寸或更高质量重试，并记下结果。国内预设的结果只记录，不影响判定：读不对时，国内预设的画面分析在设置页提示换模型 |
| 7 | 不拖慢播放 | 单次截取加编码不超过 300 毫秒，丢帧不超过 2 帧，图片不超过 1 MB |

以下只记录，供实现时处理，不决定可行性：小窗、宽屏、网页全屏、全屏、画中画、刚拖动进度条、缓冲中各截一次；标签页在后台时；加密内容能不能由扩展主动识别并拦下（规范只说这类画面可能读不出，不能指望截出来一定是黑帧）；播广告时；站内换视频后马上截；和沉浸式翻译同时开着；弹幕和控制栏会不会进截图；浏览器的可见区域截图接口作对照；各家模型收图片时的报错能不能识别成「所选模型不能看图」。第 6 项和各家模型的对照要用开发者本人的密钥，可以在截图存下来以后单独跑。

- **依赖**：实验扩展的改动和操作步骤准备好；开发者本人提供样本链接。
- **可并行**：阶段二、三。阶段四的 YouTube 部分要等字幕结论。
- **交付**：私有的实验报告；按能力写的正式字幕路线说明，写进架构设计第 6.4、14 节；PRD F02、F11 的状态更新；平台条款说明（第 8 节）里和路线有关的部分。
- **退出条件**：
  - 字幕：选出一种读取方式，同时满足下面五条。不把几种方式串成被拒就换下一种的重试链；导入字幕是独立的备用入口，不算读取方式。
    1. 读的是用户正在看的视频、平台已经在页面上提供给这位观众的字幕；不冒充其他客户端或设备，不复用、重放或伪造页面的访问凭据，不改变用户的播放器状态，不绕过登录、付费、年龄或地区限制。
    2. 在已登录的普通窗口里，播放器字幕菜单里能看到的轨都读得到正文，时间轴和视频对得上；读不到的每个样本都能归到明确的失败类别。
    3. 换视频的各种情况下，读到的字幕都属于当前视频。
    4. 「没有字幕」「字幕是空文件」「被平台限流」「需要登录」能分清。
    5. 普通用户不用复制 Cookie、取登录凭证或打开开发者控制台；整轮没有因为这种方式触发限流或人机验证，触发了就停下，降低频率后重测。
  - 选定的方式按能力写进第 8 节的 YouTube 部分，经开发者本人审阅，才作为正式路线进入阶段四。
  - 没有一种方式满足：YouTube 继续研究，两站首发都不提交商店，不改成先单发 B 站；不依赖 YouTube 的工作照常推进。
  - 画面：判定表 1–7 全部通过，解释当前画面进入实现，构建开关先关着。实现满足 PRD F11 的完成标准和用法一的拒绝条件（用法一列出的情况都不截、不发请求，其中加密内容由扩展主动识别），并在真实页面上验证过，构建开关才打开（第 9.3 节第 9 条）。任一项不通过：首发移除全部画面功能，构建开关关掉，首发的数据说明里不写截图一类；「解释当前画面」最早在更新一重新评估。
  - 记录清单里其余各项有结论；没有结论的按架构设计第 14 节的退路处理。

### 4.2 阶段二：新仓库与工具链

## 7. 权限与数据披露

权限、首次启用说明、数据说明、隐私政策和商店披露，提交前按首发的实际行为改完，几处一致。同意版本按第 7.3 节的规则升，不预先定升几次。

### 7.1 权限清单

| 声明 | 类型 | 用途 | 和现在比 |
| --- | --- | --- | --- |
| `sidePanel` | 必需 | 侧边栏 | 不变 |
| `storage` | 必需 | 设置；只存在浏览器会话里的 API 密钥 | 不变 |
| `scripting` | 必需，没有安装警告 | 用户启用 YouTube 后，动态注册打包在扩展里的脚本；安装或更新后，往已经打开的两站视频页补注入 | 首发新增 |
| B 站的三个主机：播放页、接口、字幕文件（具体写法以最终清单为准） | 必需主机 | B 站播放页的脚本和卡片；读取视频信息、字幕、官方总结、UP 主分段和稍后再看；下载字幕文件 | 不变，以最终清单为准 |
| `https://*/*` | 可选主机的声明 | 运行时逐个来源申请：启用 YouTube 时申请 YouTube 观看页的来源；保存 AI 设置时申请那一个服务地址 | 声明不变，多一种用途 |

- YouTube 不写进必需主机，也不写进静态内容脚本，在用户启用 YouTube 的那次点击里申请，拿到后动态注册。停用或收回权限后，已开的 YouTube 页面撤掉界面、停止读取。注册、注销的时机和做法见架构设计第 10.4 节。
- 运行时只申请明确的来源，不申请整个 `https://*/*`。
- 开放给网页的资源只有播放页卡片，只对 B 站。
- 解释当前画面在内容脚本里截取，不加权限。浏览器的可见区域截图要靠快捷键之类的入口，首发不做；以后真要加，先核对会不会带来新的权限警告。
- 不申请：`tabs`、`activeTab`、`cookies`、`downloads`、`debugger`、`tabCapture`、`desktopCapture`、访问所有网站、麦克风。
- 风险：宽泛的可选主机声明会不会让审核更严，没有核实，提交时留意审核意见。

### 7.2 统一授权管理

- 取代现有的回收逻辑（现有问题见第 2.1 节）。保留哪些授权、怎么回收，见架构设计第 10.4 节。

三件事分开管理，互不代替：浏览器的站点授权（第 7.1、7.2 节）、首次启用确认（在本机读取和处理哪些数据）、把内容发给模型服务的同意。说明里写什么、确认前哪些都不读，见 PRD F22 和本文第 9.2 节；本节只管版本和几处披露怎么对齐。

### 7.4 隐私政策

公开仓库里的 `PRIVACY.md` 就是隐私政策地址，不另建网站。不从旧版复制，按首发的实际行为重写：

- 联系方式：issue 地址加一个联系邮箱，邮箱由开发者本人定。
- 数据来源分三类：B 站、YouTube、用户导入的字幕文件。只按能力写，不写接口路径和签名。
- 登录状态写准：B 站的请求是扩展要求浏览器带上登录状态；YouTube 按阶段一选定的路线写。扩展不读、不存、不传 Cookie 的内容。
- 接收方：列出设置页预设的服务商，各附隐私政策链接，另写「或你自定义的地址」。
- 只在本机处理的也写：读取哪些数据（和 PRD F22 首次启用说明的清单逐项一致：视频信息、字幕、B 站官方总结和 UP 主分段、观看状态，本窗口全部生成时已授权网站标签页的地址和标题，粗筛时的稍后再看列表）、在本机做什么、存多久、怎么删。写明首次启用时扩展里有同样的说明，用户点「启用简幕」后才开始读取（第 7.3 节）。

- 存储：新的键名和库名、YouTube 的缓存、观看状态、频道偏好、推理强度、画面分析的模型、站点启用状态；截图不存。
- 权限：必需的、可选的，以及 `scripting` 的用途。
- 控制方式：停用 YouTube、收回站点权限、关掉自动生成、导出和清除。
- 政策变更：写明数据处理方式有实质变化时会在扩展里提示，按 PRD 第 9.2 节的规则写。
- 英文摘要同步改。
- 未决：商店的用户数据 FAQ 里有一条要求存储的用户数据做静态加密，这一条是否适用于扩展存在用户本机的数据，提交前要取得明确依据。在那之前，隐私政策和商店稿都不写本机资料已加密，也不只凭这一条就自行给本机数据加密。

## 8. 平台条款的可审阅说明

这份说明写简幕要满足的条件、每件事要审阅什么，以及审阅结论。它不是法律意见，也不代表平台许可。两站分别回答四件事：内容怎么获取、算不算自动访问、有没有复制、发给模型有什么依据。只按能力写。

什么时候写、什么时候审：

- YouTube 部分：阶段一选定读取路线时起草，经开发者本人审阅后路线才定下（第 4.1 节）；YouTube 的读取实现进公开仓库之前补完。
- B 站部分：B 站的读取实现进公开仓库之前写完、审阅。请求签名能不能公开和分发，另按第 4.4 节做独立评估，本节不代替那次评估。
- 提交商店前：按两站条款和 Chrome 应用商店政策的现行版本复核一次，记下核对日期和条款版本。

依据：

- YouTube 服务条款：除非服务明确允许，或事先取得 YouTube 和相关权利人的书面许可，不得访问、复制、下载、传播或以其他方式使用服务和内容；不得规避、停用或以其他方式干扰服务的任何部分，包括安全相关的功能；不得用机器人、僵尸网络、爬虫等自动方式访问服务，例外只有两种：遵守 YouTube robots.txt 的公共搜索引擎，或事先取得 YouTube 的书面许可。条款没有专为浏览器扩展写的例外。
- YouTube 官方数据接口下载字幕要求对视频有编辑权限，不能当作读取公开视频字幕的官方途径。
- 哔哩哔哩用户使用协议：未经事先明确的书面许可，不得用任何方式（包括机器人、蜘蛛、爬虫等自动程序、脚本、软件）获取平台的服务、内容和数据（第 5.6 条第 3 项）；不得修改、反向工程或反编译平台所用的软件和技术，不得恶意复制、传播这些软件、技术和材料（第 8.2、8.3 条）；产品和服务名称是其商标（第 8.4 条）。协议没有专门讲浏览器扩展的条款。
- Chrome 应用商店政策：最小权限、单一用途、用户数据的披露和有限使用。

四件事：

1. **获取：读什么、从哪读。**
   - 读取范围分三种：用户正在看的视频；B 站播放页卡片展开时，这个视频的视频信息和官方总结（PRD F14）；用户确认数量以后批量处理的条目，即当前窗口里的视频标签页（PRD F13）和用户自己的 B 站稍后再看列表（PRD F15）。读的都是平台已经提供给这位观众的内容。
   - 两站共同的条件：不冒充其他客户端或设备；不复用、重放或伪造页面的访问凭据；不绕过登录、付费、年龄或地区限制，这类内容首发不承诺；不改变用户的播放器状态；不下载音频或视频；被平台拒绝或限流时停下并提示，不换方式反复尝试，按站点退避。
   - B 站：只在用户登录后读字幕，读的是登录用户在播放页本来就能看到的内容。读取要用到 B 站接口要求的请求签名，这部分归第 4.4 节的独立评估。
   - YouTube：（待补，阶段一之后）选定的路线读的是页面上哪一类已有的数据、要不要另发请求、登录与否有什么差别。
   - 要审阅的问题：平台已经提供给这位观众的内容，能不能由扩展读取后换一种方式显示；批量处理时是否同样成立。
2. **自动访问：什么时候读、由谁触发。**
   - 都在用户点「启用简幕」确认以后；YouTube 还要用户启用 YouTube 并在浏览器里授权。
   - 打开观看页时，从页面上已有的视频元素和页面数据里取时长和频道（读得到时），用来定模式和累计播放时长，侧边栏关着也一样；这一步不另发平台请求，也不读字幕。阶段一选定的路线需要另发请求的，在这里写明。
   - B 站播放页卡片展开时，自动读取这个视频的视频信息和官方总结，收起时不读，设置页可以整体关掉（PRD F14）。
   - 打开侧边栏或点功能按钮时，为当前视频读一次字幕；开了自动生成时，获得焦点的窗口里活动标签页上打开的视频读一次；本窗口全部生成和稍后再看粗筛在用户确认数量以后逐个读取，条目之间有间隔，被限流就停。读到的缓存在本机，不重复请求。
   - 扩展没有后台抓取，不读用户自己的稍后再看以外的列表，不为别人代取。开发者这边也不跑无人值守的自动检查，真实链接检查由开发者本人手动做（第 11.3 节）。
   - 要审阅的问题：自动生成、本窗口全部生成和粗筛不是逐次点击，所以保留现有的节制（用户确认数量、条目间隔、被限流就停、只处理用户自己的列表和打开的标签页），不再放宽；这些节制够不够，审阅时看。
3. **复制：存什么、存多久、给谁。**
   - 字幕和视频信息只缓存在用户本机，有期限和条数上限，用户随时可以清除；开发者没有接收这些内容的服务器，扩展不公开、不再分发。
   - 复制和导出 SRT 由用户对当前视频手动操作，扩展不批量导出。
   - 要审阅的问题：本机缓存和用户手动导出只为用户个人观看、不提供给别人，这样是否站得住。请求签名的实现能不能公开和分发，归第 4.4 节的独立评估。
4. **发送给模型：发什么、发给谁。**
   - 只在用户完成数据同意以后发，只发当前功能需要的内容，发往用户自己选的模型服务，开发者收不到。发什么、什么时候发见 PRD 第 9 节和本文第 7.3 节。
   - 要审阅的问题：用户同意发给自选模型以后，把字幕传给第三方服务还要满足什么。B 站一侧，交给模型之前的读取适用第 1、2 项；协议里有没有其他相关条款，复核时一并看。

审阅后认为某一站站不住：这一站的读取实现不进公开仓库；首发是不带这一站的自动读取、换路线后重写这一部分，还是不提交商店，由开发者本人决定。这份说明不代表平台许可，平台可能不同意，审阅结论里照实写。

## 9. 验证与发布条件

验证由做这项工作的人完成并留下证据。验证记录、代码审查和发布决定分开记，测试通过不等于批准发布。

### 9.1 自动化检查

- 每轮改动跑 `npm run check`：类型检查、单元测试、构建、构建产物检查、公开结构检查。
- CI 里另跑页面测试 `npm run test:pages` 和端到端主流程 `npm run test:e2e`。
- 合并涉及任务和保活的改动前，在本机跑 `npm run test:e2e:lifecycle`。
- 性能敏感的改动后跑 `npm run test:perf`，和参照版本在同一台电脑上的基线对照。标准：不超出基线 20%（初值，按实测再定）；超出的逐项在 PR 里说明原因，经开发者本人确认才算通过。阶段五、七的性能条件都按这一条判。
- 单元测试不访问真实平台和模型；端到端测试里出现意外的外部请求就判失败。
- 架构设计第 3.1 节的不变量每条都要有测试，反向验证在阶段四退出前做完（第 4.4 节）。
- 覆盖的场景见架构设计第 11.3 节。跨功能的几类必须有：B 站 → YouTube → B 站切换、快速导航、分 P、切轨和导入字幕、两站并行的任务和导出归属；拒绝和收回权限、保存 AI 设置不影响站点授权、密钥进不了页面；导入旧备份、清除数据期间任务返回、存储满、模型失败；两种模拟网关；短视频直接进精读、卡片随模式展开收起；自动生成只在获得焦点的窗口里的活动视频标签页触发；首次启用确认前不读视频数据，清除全部数据后回到未启用状态；安装和更新后补注入。

### 9.2 真实 Chrome 和平台验证

在最终候选包上按实机检查清单跑。PRD 第 7 节每个功能的完成标准，清单里都有对应步骤。跨功能的几项单独列出：

- 两站样本：人工字幕、只有自动字幕、多语言轨、没有字幕、一小时以上、未登录，各有正确的结果和提示。YouTube 用阶段一的那批视频。
- 身份：两站来回切换、同站快速连续换视频、前进后退、切换标签页、扩展晚于页面加载，资料都属于当前视频，播放不被打断。
- 权限：启用、拒绝、收回、停用 YouTube，浏览器重启，扩展更新；保存 AI 设置不影响 YouTube 授权；换了 AI 地址，旧地址的权限收回。
- 首次启用：全新安装后、点「启用简幕」之前打开两站视频页，卡片和播放器图标不出现，侧边栏只显示说明，内容脚本不读页面、不计时，后台不读视频数据、不发平台请求（PRD F22）；确认以后正常读取。点「清除全部数据」后回到未启用状态，各处重新停止读取，再点「启用简幕」后恢复。
- 两次独立的浏览器会话：站点权限和资料保留；密钥按设计清空，重填后能用；service worker 冷启动正常。
- 升级路径：首发包升级到一个只改了版本号的包以后，YouTube 授权保留，动态注册按授权正确重建，已开和新开的 YouTube 页面脚本都能注入，没有新的权限警告。不要求原来的注册在更新后一直保留。全新安装另跑一遍。
- B 站页面：普通播放页、列表播放页、宽屏、网页全屏、小窗，以及从关注过的 UP 主页点进来；评论区、顶栏和播放器不受影响。
- 共存：和沉浸式翻译同时安装。
- 外观：三套主题、两种明暗、三档字号，用最终界面重新验证。
- 资料：开发者本人的真实旧备份在本机导入一次，只看结果，备份不进仓库。
- 模型：国内、海外快捷预设各跑通概览、问答、翻译和解释；四档推理强度在请求里实际生效。
- 网络、登录和平台变化造成的失败都留记录，不只展示成功的样本。

### 9.3 发布条件

以下全部满足才提交商店：

1. 两站都能完成 PRD 首发范围的核心流程，支持范围和实测一致。
2. 没有已知未处理的这些问题：串视频、资料归属错误、资料丢失、密钥泄露、等价的在途请求被重复发出、取消后又重发、停止或清除失效。重试和重新生成仍可能再次计费，不算这一条的问题；界面和商店文字也不承诺不会重复计费。
3. 第 9.1 节全部通过；第 9.2 节在最终候选包上跑完，记录绑定提交号、包校验值和浏览器版本；没覆盖的部分写明。
4. 第 8 节两站部分都经开发者本人审阅，结论是可以提交，并按现行条款复核过。不宣称上架必过。
5. 最终包、商店文字、隐私政策、首次启用说明、数据说明、截图、名称和数据披露一致；商店文字符合 PRD 第 11 节的写稿规矩。
6. 隐私政策地址公开可访问，和本次安装包一致；联系邮箱已验证；每项权限理由都已填写。
7. 两边商标库都查过，没有同类明显冲突。
8. 公开仓库全部历史扫描零命中。
9. 解释当前画面：画面实验通过，实现满足 PRD F11 的完成标准和用法一的拒绝条件并在真实页面上验证过，构建开关才打开、才进包；否则构建开关关掉，界面、文字和截图里都不出现。
10. 包里没有测试、文档、源码映射和调试文件；顶层直接是清单文件；文本都是 LF。
11. B 站请求签名的实现：第 4.4 节的独立评估已经完成、记录了依据，结论允许商店分发，商店包里才带。否则按开发者本人对范围的决定调整首发（第 12 节），商店文字和支持范围跟着改。
12. 第 7.4 节的未决项（本机数据的静态加密）有了明确依据，隐私政策和商店披露按依据写。

YouTube 的字幕路线不稳定时延后提交，两站一起延后。特殊页面或非核心功能没做完时，维持已定义的支持边界。不靠只改商店描述来宣布完成。

## 11. 竞品监控与真实链接检查

### 11.1 关注范围和做法

按来源分组定期看：同类开源项目的 issue 和发版，同类产品的更新日志和商店评价，平台官方的变化，平台对第三方工具的政策和法律动态。具体跟哪些项目留在私有清单。

GPL、AGPL 许可的项目只借思路，不用代码。

### 11.2 每周扫描

- 每周一次定时任务：扫描关注范围里的新 issue、新 PR、新版本、更新日志、新差评，以及平台官方功能、政策和法律方面的变化。扫描只读 GitHub、商店详情页、各产品的更新日志页和站外的新闻公告，不自动打开两站的视频页和其他站内页面，也不调两站的接口；两站站内的功能变化由开发者本人在日常使用中记下（第 8 节第 2 项）。
- 逐条对照简幕自查：简幕有没有同样的问题，有没有值得借的思路。
- 结果写成周报，留在私有的位置，不进公开仓库。
- 确认是简幕也有的问题，在 `jianmu` 开 issue，只写简幕自己的问题，不点名竞品，不写竞品的 issue 编号。
- 政策和法律动态在周报里单列；有新动态时，对照第 5.2 节复查一遍公开仓库的边界。平台官方功能的变化影响卖点时，按事实改 README 和商店文字。

### 11.3 真实链接手动检查

两站的真实链接检查默认由开发者本人手动做：人在页面上逐项看，不用脚本一次打开或遍历全部样本。

- 样本：两站合计十几个固定的公开视频，覆盖人工字幕、只有自动字幕、多语言轨和没有字幕几类。
- 怎么做：在开发者本人日常用的 Chrome 里，用平时的登录状态和日常用的简幕（开发构建或商店版），逐个打开样本视频的播放页和侧边栏，自己看、自己记。
- 多久一次：首发后每周一次，每站从固定样本里挑 3 个，几周轮完全部样本；每次发版前把全部样本看一遍；日常使用中发现读不到时随时查。
- 看什么：
  1. 视频信息：标题、作者、时长显示正确。
  2. 字幕轨列表：侧边栏列出的轨和播放器字幕菜单里的一致；没有字幕的样本提示「没有字幕」。
  3. 有没有被平台限流，有没有出现人机验证提示。出现了就停下这一轮，不再打开剩下的样本。
- 怎么判：结果分三类。通过。链接失效（视频被删或设为私密）：换样本。平台故障（视频信息读不到、字幕轨列表和播放器对不上、被限流、提示平台返回的格式变了）：检查适配层。YouTube 只显示空壳信息（没有标题、时长或字幕轨列表）记为平台故障。
- 怎么记：每次一行，写日期、浏览器版本、简幕版本、样本编号、三项结果和分类，有问题的加一句现象。
- 结果去哪：样本链接和记录都放在仓库外（本机或私有存档），不进公开仓库。确认要改适配层的，在 `jianmu` 开 issue，只按能力写现象（例如「读不到字幕轨列表」），不贴样本链接和平台返回的内容。
- 什么时候能改成无人值守：取得平台的明确许可，或者完成独立评估、确认有可依赖的法律依据以后，才启用无人值守的自动检查；启用前先改第 8 节的「自动访问」一项，写明做法和频率。本机运行、降低频率、不登录、不取字幕正文，都不作为取得平台许可的依据。首发不带自动检查脚本。

| 安排 B 站请求签名的独立评估，并决定评估做不成时是否接受公开版暂不自动读 B 站字幕 | 阶段四之前 | 评估覆盖公开仓库和商店安装包两种分发，记下依据；由谁做由开发者本人定。这是首发的阻断项，决定之前不改首发范围（第 4.4 节） |
| 真实链接手动检查 | 首发后每周；每次发版前 | 做法见第 11.3 节 |
| 实机检查清单里要登录、要真实账号的步骤 | 阶段四、七 | 按清单步骤操作，结果记进验证记录 |
| 确认提交商店和发布 | 阶段七 | 第 9.3 节全部满足以后 |

证据边界：

- 使用习惯只来自开发者本人，没有其他用户数据。
- 「当前已实现」以现有版本（只支持 B 站）的代码和行为为准。
- YouTube 只有本机模拟测试，没有真实页面的结果。YouTube 读取字幕（PRD F02）标首发待验证；其他功能的 YouTube 部分标首发待实现，以 F02 通过为前提；本身还要在真实页面上确认的，另标首发待验证。
- 画面截取只有规范和浏览器源码层面的推断。
- 各家模型的推理档位、图片输入限制以实现时的实测为准。
- 涉及平台接口细节的调研材料和实验结果留在私有存档，本文只写结论。
- 两站条款怎么适用，目前还没有审阅结论（第 8 节），没有法律意见，也没有取得平台许可。B 站请求签名能不能公开和分发还没有独立评估（第 4.4 节）；本机数据的静态加密要求还没有明确依据（第 7.4 节）。
