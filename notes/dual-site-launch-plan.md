# 简幕重构与双站首发方案

2026年11月9日更新。

本文写首发怎么做：分几个阶段，每个阶段依赖什么、交付什么、做到哪里算完成；新仓库怎么公开；权限、数据披露和平台条款怎么处理；验证和发布要满足哪些条件；首发后怎么迭代。产品是什么、首发和各次更新含哪些功能、每项做到哪里算完成，见[产品需求说明（PRD）](product-prd.md)。代码怎么组织、每一步的技术退出条件，见[架构设计](architecture.md)。同一件事只在一处详写，本文碰到功能细节和代码结构只给链接。

状态标注沿用 PRD 第 5.1 节：当前已实现、首发待实现、首发待验证、更新一到三、候选、不做。本文不预填验证结果，不承诺发布日期或工期。

YouTube 字幕和画面截取的现状：2026-11-05 开发者本人取消独立实验，真实页面零轮；产品实机验证待做。这两项改在产品里实现，再做真实页面验证（第 4.1 节）。

## 1. 已确定的方向

1. 目的排序：自用第一，开发者本人的公开作品第二，公开用户第三。公开发布的目标是尽量多的 GitHub 星，不定具体数字，不作承诺。不做变现，扩展里不加使用统计。成功标准见 PRD 第 2 节。
2. 主线：帮用户几分钟内判断一个长视频值不值得看、重点看哪段。
3. 先让 B 站版能日用，再迭代（开发者本人 2026-11-09 定，替代原先的「两站同时首发」）。B 站版可以单独发布；YouTube 在真实页面验证通过后才进包，可以随后续版本加入。顺序见架构设计第 12 节。
4. 首发指在 GitHub 公开发布可安装的版本：Releases 里的 zip，用户解压后在开发者模式下加载（第 7.5 节）。不提交 Chrome 应用商店，上架暂不做，以后再评估（开发者本人 2026-11-07 定，PRD 第 5.3 节）。Edge 不是前提。
5. 重构放在首发之前，和双站改造（站点适配层、统一视频身份）一起做。不再与 Digest for Bilibili 同步；内部名字、代码结构、界面和图标、提示词全部换成简幕自己的。
6. 新代码写在新建的公开仓库 `jianmu` 里，改用 TypeScript 加一个轻量构建步骤，选型和理由见架构设计第 2 节。B 站的读取实现（含请求签名）也写在这里，第 6 步进公开仓库，第 7 步接进后台后进 Releases 的 zip（第 4.4 节）。现有仓库保持私有，作为存档；现有的 PR 记录留在那里。
7. 不写自动迁移代码。发布版是一个全新的扩展，开发者本人的资料靠备份导出、导入搬过去，所以新版要能读旧格式的备份。
8. 不赶日期，越快越好。公开新仓库不等于发布，发布要满足第 9.3 节的条件。
9. 首发后小步更新，按更新一、二、三的顺序。
10. 形态不变：没有开发者后端，用户自带模型 API 密钥，资料存在本机。

本文取代此前版本里的三处做法：保留沿用自 Digest for Bilibili 的内部标识；在原仓库里小步改造、不整体重写；先让 B 站跑通新结构，再开始接 YouTube 的串行顺序（现在后台服务搭好后两边并行，见第 4 节）。

## 2. 当前事实与缺口

### 2.1 现有版本

- 只支持 B 站。发布代码约 2.6 万行，按行追溯约四成来自 Digest for Bilibili。侧边栏一个文件 4500 多行，近一半是 Digest for Bilibili 的代码。播放页卡片和稍后再看粗筛页是本项目从零写的。
- 仍和 Digest for Bilibili 一样的：4 个图标；概览、划词解释、笔记润色三份提示词；侧边栏「字幕、概览、笔记、问答」四个页签；扩展描述。三套主题是本项目加的。
- 视频身份写死成「BV 号加分 P」，散在缓存键、任务键和界面状态里，七百多处。内部标识沿用 Digest for Bilibili 的命名：27 个全局对象、7 个存储键和 IndexedDB 库名。
- 现有测试全部通过。约一半靠在隔离环境里整份运行页面或后台脚本，和现有文件布局绑死，搬不进新结构；其中不少是防 Digest for Bilibili 旧功能回来的回归测试。测试数量和旧测试的去向见架构设计第 4.4 节。
- 「回收不用的主机权限」从来没成功过：一次回收里混进了必需权限，整批被浏览器拒绝，错误又被吞掉（在 Chrome for Testing 里实测；正式版 Chrome 用同一套代码，推断一致，阶段七实机再核对一次）。现有隐私政策里「换了地址再保存，旧地址的权限会收回」现在不成立。
- 数据同意是一个全局版本号，现为 2，严格相等才放行。界面分不出「从没同意过」和「说明更新了」。
- 国内快捷预设的默认模型名是服务商列出的旧名：服务商说旧名仍然接受，但对应的旧模型已经退役，请求改由新模型处理。

### 2.2 YouTube 和画面截取

- YouTube 只有本机模拟测试，从没在真实页面上得到结果。YouTube 读取字幕首发待验证。
- 画面截取只有规范和浏览器源码层面的推断：在内容脚本里把页面上的视频画到画布上，普通视频应当不用新权限；从侧边栏点按钮拿不到浏览器可见区域截图的权限。都没在真实页面上验证。
- 2026-11-05 开发者本人取消独立实验，真实页面零轮；产品实机验证待做。

### 2.3 发布、名称和平台

- 还没有发布过可安装的版本。首发走 GitHub Releases，安装和更新的约束见第 7.5 节。
- 隐私政策没有公开地址。现有隐私政策写着「尚未发布的开发版」、没有联系方式，还写了 B 站接口签名的细节。首发要重写。
- 图标仍是 Digest for Bilibili 的。旧实机检查清单约一半的步骤没跑过。
- 「简幕」初查没有同名产品，还没查过官方商标库。开发者本人账号下的 `jianmu` 仓库名可用；GitHub 上另有同名但不同类的项目（例如 DevOps 工具「建木」），搜索时会混在一起。
- 两站的条款都限制未经许可用自动方式获取内容，都没有专门讲浏览器扩展的条款；YouTube 服务条款另外限制复制、下载内容和规避限制。各条的内容和简幕要满足的条件见第 8 节。
- 同类开源项目有因平台或权利方的要求而关停或停更的先例，说明平台会对这类项目采取行动。
- 没有使用数据。产品判断依据的是开发者本人的使用习惯（PRD 第 3 节）。

## 3. 首发范围

首发包含什么以 PRD 第 5.2 节为准，这里只概括：

- 重写：内部名字、代码结构、界面和图标、提示词。
- 两站跑通现有功能；B 站专属的官方材料、播放页卡片、稍后再看粗筛保留；本窗口全部生成处理窗口里的 B 站视频，YouTube 标签页只在本机清点，本批跳过（PRD F13）。B 站的读取实现进公开仓库和发布包，限制见第 4.4 节。
- 两站共同的主流程是单视频：用户在支持的普通观看页取得平台原生字幕，看到结论和章节，做引用问答。YouTube 的例外：用户要多做一次手动操作才读到字幕（PRD F02）；自动生成和本窗口全部生成首发统一跳过 YouTube，YouTube 走单视频手动生成（PRD F10、F13）。这是产品决定，不是待定项。两站首发成立的条件是两站都走通这条主流程。YouTube 多一次手动操作可以接受；只能导入字幕文件、只能看到标题，都不算成立。
- 首次启用确认（PRD F22）；速览、精读两种模式和自动切换；悬停才出现的笔记图标；每个功能单独调推理强度；自动生成总开关（默认关），打开后打开 B 站视频就生成概览。
- 解释当前画面：首发待验证。第 11 步直接写产品代码，用画面验证构建验证；发行开关打开前，实现要满足 PRD F11 的完成标准、用法一的拒绝条件和第 4.5 节的量化标准。画面验证失败或缺少关键证据，首发移除全部画面功能，不拖首发；「解释当前画面」最早在更新一重新评估，画面信息并入概览、笔记里插关键画面仍按原计划和各自的前提推进，不承诺更新一全部上线。
- 发布必需的工作：隐私政策、README 和它用的截图、演示 GIF、商标检索、平台条款说明（第 8 节）。

支持范围：YouTube 首批只支持桌面普通观看页上已有字幕的视频；B 站保留现有范围，含分 P（PRD F01）。首发不做的见 PRD 第 5.3、5.4 节，首发后的更新见本文第 10 节。

### 4.1 阶段一（已取消）：YouTube 字幕和画面截取的可行性实验

2026-11-05 开发者本人取消独立实验，真实页面零轮；产品实机验证待做。阶段一保留编号，不再做单独的实验扩展。要回答的两件事不变，改在产品里实现，再做真实页面验证：

- YouTube 上有没有一种普通用户能用、不规避平台限制的方式读取已有字幕：第 10 步（架构设计第 12 节，归阶段四），见第 4.4 节。
- 在页面里截取当前画面能不能稳定拿到正确的帧：第 11 步（架构设计第 12 节，归阶段五），见第 4.5 节。

第 3–9 步按各自的进入和退出条件推进。第 10、11 步在第 9 步切换日用之后开工（开发者本人 2026-11-09 定，架构设计第 12 节）。

YouTube 字幕读取路线要同时满足下面五条。不把几种方式串成被拒就换下一种的重试链；导入字幕是独立的备用入口，不算读取方式。

1. 读的是用户正在看的视频、平台已经在页面上提供给这位观众的字幕；不读 Cookie 内容，不自行计算或构造平台用于校验请求访问权限的数据，不冒充其他客户端或设备，不复用、重放或伪造页面为自身请求取得的校验信息，不引起机器翻译字幕轨的请求，读取时不改变用户的播放器状态（用户点时间点引起的跳转和开始播放另算），不绕过登录、付费、年龄或地区限制。代开和代换语言按下面的判据。
2. 在已登录的普通窗口里，播放器提供给这位观众的每条人工轨和原语言自动轨都读得到完整正文，时间轴和视频对得上。参照物是播放器，不是文字稿面板的语言菜单：验证者可以逐条手选核对，产品不用自动遍历。播放器有一条人工轨而面板没列出，或长视频只读到当前可见的几十句，都不算通过。有轨却读不到的样本要归到明确的失败类别，归了类也不算通过。这一条说的是逐轨读得到，不是产品自动选轨：YouTube 上默认读面板当前选中的原生轨（PRD F02）。最后只做得到「当前面板可见的一轨」时，是再次缩小支持范围，要另定，不能换个分母算通过。
3. 换视频的各种情况下，读到的字幕都属于当前视频。这条是发布阻断。地址和播放器都换到新视频时，文字稿面板可能还留着旧视频的内容，所以开始读、正文返回、写缓存前都要核对视频、导航代次和所选轨，并能证明面板内容已经更新。快速切换、前进后退、晚注入或换轨时无法归属的结果一律丢弃。
4. 「没有字幕」「字幕是空文件」「被平台限流」「需要登录」各有可辨的信号才报。面板没打开是待用户操作；找不到入口可能是页面变了；加载中或空白不能直接报「字幕是空文件」。「需要登录」只在平台明确要求登录时报，明确信号是什么，第 10 步实测后定；只看到空文件时报空文件，提示登录或导入，不判定为需要登录。其余报「暂时无法读取」，可以如实提示，但不算这四种情况已经分清。识别不了限流时，简幕代操作页面一律不启用（第 4.4 节）。实机没遇到限流时，限流这一项记未覆盖，不算已分清：代操作默认不开，要开由开发者本人记进审阅记录；第 1 档未覆盖的部分按「暂时无法读取」提示，是否接受带这项未覆盖发布，开发者本人记进审阅记录。错误处理用模拟补测，这只证明产品按信号处理，不证明信号是真的。
5. 普通用户只用正常界面，不用复制 Cookie、取登录凭证或打开开发者控制台；开发者可以在验证时观察网络。整轮没有因为这种方式触发限流或人机验证。遇到限流或人机验证立即停下，按第 4.4 节的实机清单处理。实机没遇到限流或人机验证，只说明那一轮的结果。

第 1 条里按设计能定的部分（只读前台的当前视频、不碰 Cookie、不另发字幕请求）和第 5 条里普通用户的操作门槛，「选定候选路线」时按设计判断。第 1 条里的机器翻译和播放器状态，第 2、3、4 条，第 5 条里的限流、人机验证，要到「路线实机通过」才有结论。五条都不能在「选定候选路线」时整体算过。

第 1 条里的复用限制按严格读法判，判据是这次请求是谁要的，不看请求由谁发出：

- 用户自己操作 YouTube 页面引起的请求，是观众操作平台界面引起的。
- 用户在简幕里点一次，能证明用户有这次意图，不等于用户亲自操作了页面。页面因此向平台取文字稿时，这次平台访问的触发方是简幕。所以这种操作只能按「用户逐次委托简幕操作 YouTube 页面」设计，条件见 PRD F02，这也不是平台许可。
- 页面因此取文字稿时，第 2 档和代换语言在严格读法下不满足第 1 条。只有开发者本人在审阅记录里单独记下接受这个明确例外才保留，这是项目例外，不是平台许可；没有这条记录就按第 4.4 节退。这条决定留到第 10 步由开发者本人做，现在不预设结果。
- 自动生成的总开关和本窗口全部生成的确认，都不是用户对这个视频当次的操作，不能让简幕打开面板或换语言。
- 另发请求读字幕轨不通过：这次请求是简幕要的，不是用户操作页面引起的。这是按设计的判断，没有实测。

原来的记录清单和画面判定表不再单独跑一轮，各项去向如下。到第 10、11 步仍没有结论的，按架构设计第 14 节的退路处理。

| 原来的项目 | 现在 |
| --- | --- |
| 每个视频的字幕轨、音频语言、多音轨；已登录和未登录对照；换视频；频道编号和简介；其他扩展、人机验证提示、播放器状态 | 第 10 步的实机清单（第 4.4 节） |

    - 参照：先看播放器实际给这位观众什么，再判断扩展读得对不对。在已登录的普通窗口和未登录的无痕窗口对照，以播放器提供给这位观众的人工轨和原语言自动轨为准，验证者逐条手选核对，产品不自动遍历。排除按需生成的机器翻译字幕轨，扩展也不能通过操作播放器或文字稿面板间接引起这类请求。

    1. 第一次截帧之前，先完成覆盖「读取当前单帧，用于解释画面」的首次启用确认（PRD F22）。然后在画面验证构建上验证截帧：两站普通视频能唯一找到主视频，读出与屏幕一致的当前帧，并能在截取前主动识别加密播放。保护状态无法可靠判断时拒绝。用产品内容脚本的输出对照屏幕，不为此给发行构建新增主世界脚本。截图不落盘。
    2. 截帧过了，再接模型和两个用户入口。第一次用画面验证构建向真实模型发截图之前，先完成覆盖截图的数据同意。
    3. 按下表、PRD F11 的完成标准和用法一的拒绝条件逐项核对。
    4. 通过后才打开发行开关，并在最终候选包回归（第 9.3 节第 9 条）。

    下表判断的是截帧能不能做，不是某一家模型能不能看图。任一项不通过，走下面的退路：

    | 测什么 | 通过标准 |
    | --- | --- |
    | 找到主视频 | 两站普通样本都能唯一找到主视频元素。遇到 B 站的特殊播放器元素单独记下，另测能否取到画面 |
    | 读得出像素 | 普通样本（不含番剧、电影、付费内容）全部不报安全错误 |
    | 不是黑帧或空帧 | 暂停在非黑场画面时，截图和屏幕所见一致，平均亮度高于 8/255 |
    | 是当前这一帧 | 暂停时和屏幕一致；播放中截到的帧和点击时的播放位置相差不超过 0.2 秒 |
    | 模型读得出字 | 5 个幻灯片或代码样本，用实际编码结果验证：按实际播放清晰度截图，长边缩到 1456、JPEG 质量 0.85。至少海外预设的一个能看图的模型逐字读对标题和至少 3 行正文或代码；读不对时换更大尺寸或更高质量重试，并记下结果。国内预设的结果只记录，不影响判定：读不对时，国内预设的画面分析在设置页提示换模型 |
    | 不拖慢播放 | 单次截取加编码不超过 300 毫秒，丢帧不超过 2 帧，图片不超过 1 MB |
    | 拒绝条件 | 按 PRD F11 用法一逐项核对：找不到视频、画面还没就绪、加密播放、标签页在后台、正在播广告、截帧时视频已换、所选模型不能看图，都不截、不发请求，并说明原因 |

    - 样本：第 10 步样本里画面有幻灯片、代码或图表的视频，加上 B 站的知识区幻灯片、代码教程、分 P、番剧或电影各至少一个。B 站视频只跑画面部分。YouTube 样本用第 4.4 节的 Chrome 配置和测试账号。

    - 悬停图标：在真实页面核对两站控制栏显隐的页面信号，以及 `n` 键在 YouTube 上会不会冲突。这两项属于 PRD F08，解释当前画面验证失败或被移除时也要做完。
    - 广告：YouTube 的片头和片中广告各看一次，B 站看普通视频有没有播放器广告，核对 `findMainVideo()` 的结果、定模式用的时长、播放计时、存笔记、点字幕跳转，以及悬停图标不挡广告控件。这些不属于画面功能，解释当前画面验证失败或被移除时也要做完。环境里看不到广告的，记为未覆盖。

  - 首次启用说明和数据说明跟着功能写，规则见 PRD 第 9.2 节，版本号见第 7.3 节。开发者本人切换日用时同意的是当时那一版；之后加进来的功能扩大了发送范围（例如打开 B 站视频自动发送、画面截图），先升版、重新同意，再在开发构建里启用；扩大了本机读取范围（例如当前单帧），同样先升版、重新确认。

## 7. 权限、数据披露和安装更新

权限、首次启用说明、数据说明和隐私政策，发布前按首发的实际行为改完，几处一致。同意版本按第 7.3 节的规则升，不预先定升几次。

### 7.1 权限清单

| 声明 | 类型 | 用途 | 和现在比 |
| --- | --- | --- | --- |
| `sidePanel` | 必需 | 侧边栏 | 不变 |
| `storage` | 必需 | 设置；API 密钥默认只存在浏览器会话里，用户选了记住才存在本机（怎么写见第 7.4 节） | 不变 |
| `scripting` | 必需，没有安装警告 | 用户启用 YouTube 后，动态注册打包在扩展里的脚本；安装或更新后，往已经打开的两站视频页补注入 | 首发新增 |
| B 站的三个主机：播放页、接口、字幕文件（具体写法以最终清单为准） | 必需主机 | B 站播放页的脚本和卡片；读取视频信息、字幕、官方总结、UP 主分段和稍后再看；下载字幕文件 | 不变，以最终清单为准 |
| `https://*/*` | 可选主机的声明 | 运行时逐个来源申请：启用 YouTube 时申请 YouTube 观看页的来源；保存 AI 设置时申请那一个服务地址 | 声明不变，多一种用途 |

- YouTube 不写进必需主机，也不写进静态内容脚本，在用户启用 YouTube 的那次点击里申请，拿到后动态注册。停用或收回权限后，已开的 YouTube 页面撤掉界面、停止读取。注册、注销的时机和做法见架构设计第 10.4 节。
- 运行时只申请明确的来源，不申请整个 `https://*/*`。
- 带密钥的请求不跟随重定向，服务地址跳到别处时密钥不会被带过去。
- 开放给网页的资源只有播放页卡片，只对 B 站。
- 解释当前画面在内容脚本里截取，不加权限。浏览器的可见区域截图要靠快捷键之类的入口，首发不做；以后真要加，先核对会不会带来新的权限警告。
- 不申请：`tabs`、`activeTab`、`cookies`、`downloads`、`debugger`、`tabCapture`、`desktopCapture`、访问所有网站、麦克风。
- 权限最小化不因为不上架而放宽：用不到的权限不声明，上面不申请的照样不申请。

### 7.2 统一授权管理

- 取代现有的回收逻辑（现有问题见第 2.1 节）。保留哪些授权、怎么回收，见架构设计第 10.4 节。
- 要验证的场景：授予、拒绝、在浏览器里收回、用户停用、浏览器重启、扩展更新和已开的标签页；保存 AI 设置不影响站点授权。测试替身按浏览器实测的形状返回已授权列表。
- 发布约束：修好并在实机上验证以后，隐私政策才写回收的说明，而且不写成无条件承诺：尝试回收不再需要且能安全单独移除的旧授权；覆盖关系、无法识别或浏览器回收失败可能导致授权保留。

### 7.3 首次启用确认和数据同意

三件事分开管理，互不代替：浏览器的站点授权（第 7.1、7.2 节）、首次启用确认（在本机读取和处理哪些数据）、把内容发给模型服务的同意。说明里写什么、确认前哪些都不读，见 PRD F22 和本文第 9.2 节；本节只管版本和几处披露怎么对齐。

首次启用确认：

- 只在本机处理的数据也要披露，显著披露和同意在扩展自己的界面里完成，只写在 README 或隐私政策里都不算。浏览器的主机授权框只说明能访问哪个网站，不说明用途，简幕也不拿它代替这一步，由首次启用确认承担。
- 首次启用说明、隐私政策（第 7.4 节）和 README 写到的读取范围要一致。本机读取的内容或用途有实质变化时，几处同步改；要不要请用户重新确认，按 PRD F22 的规则。
- 版本和数据同意分开记，启用说明从 1 起，做法相同（架构设计第 10.2 节）：要重新确认就升版，旧确认随之失效；开发期间也一样，开发者本人切换日用时确认过的说明也算。当前单帧这一条只在解释当前画面进包时进说明；发行开关关着的构建停在不含这一条的版本，画面功能以后上线时再加，并请用户重新确认。YouTube 的代开和代换语言同样只在进包时进说明。

数据同意：

- 只启用 YouTube 不调模型，也不批量读取任何列表。YouTube 的字幕只在用户当次操作后读取，自动生成和本窗口全部生成不读 YouTube 字幕。
- 首发的数据说明写清三类变化：两个站、画面截图（画面功能进首发时）、打开 B 站视频自动发送。说明里写什么见 PRD 第 9.2 节。
- 什么时候要更新说明、什么时候要重新同意，规则见 PRD 第 9.2 节。本节只管版本号：
  - 要重新同意就升版，旧同意随之失效，代码里另用说明内容的指纹兜底（架构设计第 9.4 节）。开发期间也一样：开发构建里有人同意过某一版说明以后（包括开发者本人切换日用以后），再扩大范围就升版；还没有人同意过的草稿可以合成一版。
  - 版本号从现在的 2 往上加，首发时是几，由开发期间实际升过几次决定，不预先定。
  - 发布版是新扩展，首发对所有人都是第一次同意；以后说明更新时界面怎么提示，见 PRD 第 9.2 节。
  - 首发以后各次更新要评估的项见第 10 节。
- 要同步的地方：设置页的数据说明、首次启用的说明、代码里「每个同意版本新增了哪些内容」的表、`PRIVACY.md`、README。改一处就同步其他几处。数据处理方式有实质变化时要主动告诉用户。
- 速览的提问入口和重点章节都没有扩大同意范围：问题和相关字幕仍是用户手动提交才发，重点只在原来的结论请求里多返回几个起点，不另发请求。这两项不升版，不加同意条目。
- 这个版本号是项目自己的机制，不是 Chrome 规定的字段。

### 7.4 隐私政策

公开仓库里的 `PRIVACY.md` 就是隐私政策地址，不另建网站。不从旧版复制，按首发的实际行为重写。骨架可以先写，按第 10 步实测的路线和最终候选包定稿：

- 头部：新名称；生效日期为首发日；只写 GitHub 发布版；没有「开发版」之类的说法；不写分叉来源。
- 联系方式：issue 地址加一个联系邮箱，邮箱由开发者本人定。
- 数据来源分三类：B 站、YouTube、用户导入的字幕文件。只按能力写，不写接口路径和签名。
- 登录状态写准：B 站的请求是扩展要求浏览器带上登录状态；YouTube 按第 10 步实测的路线写，浏览器是否随请求带上登录状态、是否另发平台请求、请求由什么动作触发，这三项等「路线实机通过」再定稿；简幕打开文字稿面板或切换面板语言时页面因此发请求的，如实写。「扩展不读取 Cookie 内容」和「浏览器是否随请求带上登录状态」分开交代：扩展不读、不存、不传 Cookie 的内容。
- 接收方：列出设置页预设的服务商，各附隐私政策链接，另写「或你自定义的地址」。
- 只在本机处理的也写：读取哪些数据（和 PRD F22 首次启用说明的清单逐项一致：视频信息、字幕、B 站登录状态（只看是否已登录）、B 站官方总结和 UP 主分段、观看状态，本窗口全部生成时已授权网站标签页的地址和标题，粗筛时的稍后再看列表和每个视频看到哪里，解释当前画面进包时用户点击后读取的当前单帧）、在本机做什么、存多久、怎么删。写明首次启用时扩展里有同样的说明，用户点「启用简幕」后才开始读取（第 7.3 节）。
- 按功能写发送什么、什么时候发：点按钮才发的；打开自动生成后自动发的（首发只有 B 站）；解释当前画面的截图（上线时）。写明模型服务怎么处理这些内容，看该服务自己的政策，简幕不能保证。
- 标签页：只看得到已授权网站（B 站、启用了的 YouTube、填了的 AI 服务地址）标签页的地址和标题。
- 存储：新的键名和库名、YouTube 的缓存、观看状态、频道偏好、推理强度、画面分析的模型（解释当前画面上线时）、站点启用状态；截图不存。
- 密钥：默认只存在浏览器会话里。发布版带记住密钥，勾选框默认不勾，中英文都写清：这是和 AI 发送同意分开的单独选择，勾选后以未加密形式保存在本机，不进入简幕导出的备份、不同步，共用电脑不要开。取消勾选后，扩展删除本机保存的密钥记录，改为仅在本次浏览器会话中使用。清除密钥、清除全部数据，或更换服务商、自定义地址导致密钥来源不匹配并保存后，旧密钥会从当前配置中移除。删除或替换记录后，浏览器的存储文件中仍可能残留旧密钥明文，扩展无法保证擦除。卸载扩展时 Chrome 会删除该扩展的本地数据，但这不代表安全擦除，也不保证删除系统备份中的副本。担心泄露时，请到服务商后台撤销这把密钥。勾选说明、取消记住后的提示、清除确认和成功提示、隐私政策都按这个说法写，中英文同步，不宣传可以彻底擦除，随这个功能发布前完成。
- 权限：必需的、可选的，以及 `scripting` 的用途。
- 控制方式：停用 YouTube、收回站点权限、关掉自动生成、导出和清除。
- 政策变更：写明数据处理方式有实质变化时会在扩展里提示，按 PRD 第 9.2 节的规则写。
- 英文摘要同步改。
- 加密：不写本机资料已加密（第 9.3 节第 12 条）。

### 7.5 安装与更新

- 安装：用户打开浏览器的开发者模式，解压 Releases 里的 zip，手动加载解压出的文件夹。
- 更新：没有自动更新。用户解压新版覆盖同一文件夹，再重新加载。
- 覆盖更新后能否保留扩展身份和本地数据：首发待验证（第 9.2 节）。不通过时先不发布，另外审阅迁移方案或调整范围。备份不含导入的字幕、译文和频道偏好（PRD F20），不靠改 README 接受这些资料丢失。
- 构建带固定的 `key`，扩展身份从第一个公开版本起就稳定。清单没有 `key` 时，身份跟着文件夹路径走；首发不带、以后再加，身份会变，已安装用户的本机数据接不上。这是按 Chrome 机制的判断，没在本项目实测。第 12 步打候选包之前写进 `manifest.template.json`（架构设计第 2、11.2 节）。
- 版本检查不加，不新增对外请求。

## 8. 平台条款的可审阅说明

本节记录两站在获取、自动访问、复制和发送给模型方面的实现条件。YouTube 部分另列条款审阅问题，按下文规定的时点审阅和复核；B 站部分按实现条件自查，条款摘录只作参考，不要求形成条款适用结论。本节不是法律意见，也不代表平台许可，具体记录留在私有存档。两站分别回答四件事：内容怎么获取、算不算自动访问、有没有复制、发给模型有什么依据。只按能力写。

本节写首发必须做到的条件，现有版本不一定做到，做到之前这些句子不算成立，状态以 PRD 为准。

接受项目风险和平台许可是两件事，分开记：

- 项目风险：开发者本人 2026-11-05 决定接受平台可能不同意的风险，按本节的条件继续。这是项目自己的决定。
- 平台许可：两站都没有给过。本节的任何条件都不等于平台许可。

什么时候写、什么时候审：

- YouTube 部分：第 10 步「选定候选路线」时起草这条路线的条款说明，经开发者本人审阅；读取实现首次推到公开分支或出现在公开 PR 之前，按实际行为补完，再经开发者本人审阅；这次另审复制和发送给模型两项；「路线实机通过」以后按实测路线定稿（第 4.4 节）。
- B 站部分：读取实现按既定安排公开，遵守本节的实现条件；发布前在最终候选包上逐项自查，结果留在私有验证记录。
- 发布前：YouTube 部分按实测路线、最终候选包和条款的现行版本复核一次，核对日期、地区和条款版本记进审阅记录；B 站部分对照本节的条件自查一遍。

依据：

1. **获取：读什么、从哪读。**
   - 读取范围分三种：用户正在看的视频；B 站播放页卡片展开、且标签页到过前台时（首发待实现），这个视频的视频信息和官方总结（PRD F14）；用户确认数量以后批量处理的条目，即当前窗口里的 B 站视频标签页（PRD F13）和用户自己的 B 站稍后再看列表及每个视频看到哪里（PRD F15）。本窗口全部生成在用户确认之前只看标签页的地址和标题、查本机已有的结果，不读平台内容（首发待实现）。YouTube 的字幕只读用户正在看的视频，标签页没到前台时不读（首发待验证）。读的内容以平台提供给这位观众的为限。YouTube 文字稿面板的内容可能在简幕打开面板时才向平台取来，待真实页面确认。B 站官方总结附带的字幕是否对观众可见待确认，确认之前不用。

   - B 站（首发待实现）：只在用户登录后读平台内容，读的是登录用户在播放页本来就能看到的内容。字幕文件读取被限流也按限流处理，不再试下一条轨，也不重新列轨。读取依赖 B 站接口要求的请求签名和相关读取实现，这部分公开，进公开仓库和发布包（第 4.4 节）。不碰付费内容，付费状态确认不了时也不读，保持低频。
   - YouTube（首发待验证）：这条路线读观看页文字稿面板里显示的文字和时间，是第 10 步的候选设计（第 4.4 节）。文字稿面板是平台给观众的功能，这不代表平台同意扩展读取。
     - 谁操作页面：第 1 档由用户自己打开面板，简幕读面板里已经显示的文字和时间，这时的平台请求由用户操作页面引起。第 2 档由用户逐次委托简幕打开一次面板，条件见 PRD F02；页面因此向平台取文字稿（待真实页面确认），这是简幕引起的平台访问。用户在简幕里点一次，证明的是这次意图，不等于用户亲自操作了页面，也不是平台的书面许可。代换语言由用户逐次委托简幕切换一次面板语言，页面因此取文字稿时，同样是简幕引起的平台访问。这两种情况在严格读法下不满足第 4.1 节第 1 条，要有下面的例外记录才保留。

2. **自动访问：什么时候读、由谁触发。**

3. **复制：存什么、存多久、给谁。**
   - 字幕和视频信息的缓存只在用户本机，有期限和条数上限，用户随时可以清除。平台返回的字幕地址不落盘（首发待实现）。粗筛读到的列表和官方总结存在本机，有期限（首发待实现），可以清除。用户保存的概览、问答、笔记和译文长期留在本机，保存到用户删除为止，笔记可以含字幕片段。开发者收不到这些内容，扩展自身不公开它们；用户用 AI 功能时，内容会发给用户选的模型服务（第 4 项）。
   - 复制和导出 SRT 由用户对当前视频手动操作，字幕全文不批量导出。用户可以手动导出粗筛结果（含官方总结）、全部笔记和备份（含笔记里的字幕片段、概览和问答），都由用户点击，存到用户自己的设备。

审阅后认为 YouTube 这部分站不住：代开或代换语言站不住的，按第 4.4 节的失败层级退；这条路线本身站不住的，读取实现不进公开仓库，换路线后重写这一部分；YouTube 找不到满足条件的路线，B 站版照常发布，YouTube 不进包。B 站适用于首发的实现条件未满足或缺少验证依据时，不满足发布条件，应先修复或调整实现并重新自查。若要改变首发范围或这些条件，须由开发者本人另行决定并同步 PRD 与本方案；在此之前，仍按第 9.3 节的全部条件执行。

README 和 Releases 页面里的站名：保留「适用于哔哩哔哩和 YouTube™」，加无关联声明（PRD 第 11 节），不写合作、官方这类字样，不用平台标志。这是说明适用哪个网站，平台可以不这样看，协议第 5.10、8.4 条记为剩余限制。

## 9. 验证与发布条件

验证由做这项工作的人完成并留下证据。验证记录、代码审查和发布决定分开记，测试通过不等于批准发布。

### 9.1 自动化检查

- 每轮改动跑 `npm run check`：类型检查、单元测试、构建、构建产物检查、公开结构检查。
- CI 里另跑页面测试 `npm run test:pages` 和端到端主流程 `npm run test:e2e`。
- 合并涉及任务和保活的改动前，在本机跑 `npm run test:e2e:lifecycle`。
- 性能敏感的改动后跑 `npm run test:perf`，和参照版本在同一台电脑上的基线对照。标准：不超出基线 20%（初值，按实测再定）；超出的逐项在 PR 里说明原因，经开发者本人确认才算通过。阶段五、七的性能条件都按这一条判。
- 单元测试不访问真实平台和模型；端到端测试里出现意外的外部请求就判失败。
- 架构设计第 3.1 节的不变量每条都要有测试，反向验证在阶段四退出前做完（第 4.4 节）。
- 这三项回归必须有：问答抽屉开着时自动切换后仍能撤销；重新生成停在写结论这一步不丢旧概览；带重点的概览备份往返，旧备份导入后没有重点。

### 9.2 真实 Chrome 和平台验证

在最终候选包上按实机检查清单跑。PRD 第 7 节每个功能的完成标准，清单里都有对应步骤。跨功能的几项单独列出：

- 两站样本：人工字幕、只有自动字幕、多语言轨、没有字幕、一小时以上、未登录，B 站另加付费和充电专属视频，各有正确的结果和提示。YouTube 用第 10 步建立的样本在最终候选包上复核，账号、参照、记录和停止规则同第 4.4 节的实机清单。解释当前画面进包时，第 11 步建立的样本也在最终候选包上复核。
- 双站核心流程和跳过行为：两站都用平台原生字幕走通单视频主流程，取得字幕，看到结论和章节，做引用问答；YouTube 按第 10 步定下的档位走，读到后显示实际轨道。混开两站的窗口里，本窗口全部生成按 PRD F13 清点、标注和跳过 YouTube 条目，确认文案的数量和实际处理的一致；打开 YouTube 视频不触发自动生成和自动翻译。
- 身份：两站来回切换、同站快速连续换视频、前进后退、切换标签页、扩展晚于页面加载，资料都属于当前视频，播放不被打断。
- 权限：在侧边栏里点「在 YouTube 上启用」能不能直接弹出授权框；启用、拒绝、收回、停用 YouTube，浏览器重启，扩展更新；保存 AI 设置不影响 YouTube 授权；换了 AI 地址，不再需要且能安全单独移除的旧授权收回，架构设计第 10.4 节列的保留情况照旧留着。
- 首次启用：全新安装后、点「启用简幕」之前打开两站视频页，卡片和播放器图标不出现，侧边栏只显示说明，内容脚本不读页面、不计时，后台不读视频数据、不发平台请求（PRD F22）；确认以后正常读取。点「清除全部数据」后回到未启用状态，各处重新停止读取，再点「启用简幕」后恢复。启用说明有实质变化的包装上以后旧确认失效，重新确认后恢复；只改版本号的包不要求重新确认。
- 两次独立的浏览器会话：站点权限和资料保留；service worker 冷启动正常。默认模式重启后清空，重填后能用。记住密钥再验三条：记住模式重启后还在，不用重填；取消记住后接口读不到本机记录，本次会话仍可用，重启后要重填；保存更换服务商或来源不同的自定义地址后，接口读不到旧记录，旧密钥不再发出。这些检查只说明接口读不到、行为正确，不说明磁盘已经擦净。
- 升级路径：把一个只改了版本号的包解压覆盖首发包的文件夹，重新加载以后，核对扩展身份和本地数据有没有保留（第 7.5 节）；YouTube 授权保留，动态注册按授权正确重建，已开和新开的 YouTube 页面脚本都能注入，没有新的权限警告。不要求原来的注册在更新后一直保留。全新安装按 README 的步骤另跑一遍。
- B 站页面：普通播放页、列表播放页、宽屏、网页全屏、小窗，以及从关注过的 UP 主页点进来；评论区、顶栏和播放器不受影响。
- 共存：和沉浸式翻译同时安装。
- 外观：三套主题、两种明暗、三档字号，用最终界面重新验证。
- 资料：开发者本人的真实旧备份在本机导入一次，只看结果，备份不进仓库。
- 模型：国内、海外快捷预设各跑通概览、问答、翻译和解释；四档推理强度在请求里实际生效。
- 网络、登录和平台变化造成的失败都留记录，不只展示成功的样本。

## 11. 竞品监控与真实链接检查

### 11.1 关注范围和做法

按来源分组定期看：同类开源项目的 issue 和发版，同类产品的更新日志和商店评价，平台官方的变化，平台对第三方工具的政策和法律动态。具体跟哪些项目留在私有清单。

GPL、AGPL 许可的项目只借思路，不用代码。

### 11.2 每周扫描

- 每周一次定时任务：扫描关注范围里的新 issue、新 PR、新版本、更新日志、新差评，以及平台官方功能、政策和法律方面的变化。扫描只读 GitHub、商店详情页、各产品的更新日志页和站外的新闻公告，不自动打开两站的视频页和其他站内页面，也不调两站的接口；两站站内的功能变化由开发者本人在日常使用中记下（第 8 节第 2 项）。
- 逐条对照简幕自查：简幕有没有同样的问题，有没有值得借的思路。
- 结果写成周报，留在私有的位置，不进公开仓库。
- 确认是简幕也有的问题，在 `jianmu` 开 issue，只写简幕自己的问题，不点名竞品，不写竞品的 issue 编号。
- 政策和法律动态在周报里单列；有新动态时，对照第 5.2 节复查一遍公开仓库的边界。平台官方功能的变化影响卖点时，按事实改 README。

### 11.3 真实链接手动检查

两站的真实链接检查默认由开发者本人手动做：人在页面上逐项看，不用脚本一次打开或遍历全部样本。

- 样本：两站合计十几个固定的公开视频，覆盖人工字幕、只有自动字幕、多语言轨和没有字幕几类。
- 怎么做：B 站样本在开发者本人日常用的 Chrome 里，用平时的登录状态；YouTube 样本用第 4.4 节的 Chrome 配置和测试账号。简幕用日常的版本（开发构建或发布版），逐个打开样本视频的播放页和侧边栏，自己看、自己记。
- 多久一次：首发后每周一次，每站从固定样本里挑 3 个，几周轮完全部样本；每次发版前把全部样本看一遍；日常使用中发现读不到时随时查。
- 看什么：
  1. 视频信息：标题、作者、时长显示正确。
  2. 字幕轨列表：B 站看侧边栏列出的轨和播放器字幕菜单里的是否一致；YouTube 按第 4.4 节的参照，以播放器已提供的人工轨和原语言自动轨为准，按需生成的机器翻译字幕轨不算，例行检查只用测试账号的登录状态，不另开未登录窗口对照；没有字幕的样本提示「没有字幕」。
  3. 有没有被平台限流，有没有出现人机验证提示。出现了就停下这一轮，不再打开剩下的样本。
- 怎么判：结果分三类。通过。链接失效（视频被删或设为私密）：换样本。平台故障（视频信息读不到、字幕轨列表和上面的参照对不上、被限流、提示平台返回的格式变了）：检查适配层。YouTube 只显示空壳信息（没有标题、时长或字幕轨列表）记为平台故障。
- 怎么记：每次一行，写日期、浏览器版本、简幕版本、样本编号、三项结果和分类，有问题的加一句现象。
- 结果去哪：样本链接和记录都放在仓库外（本机或私有存档），不进公开仓库。确认要改适配层的，在 `jianmu` 开 issue，只按能力写现象（例如「读不到字幕轨列表」），不贴样本链接和平台返回的内容。
- 什么时候能改成无人值守：取得平台的明确许可，或者另行完成针对无人值守检查的独立评估、确认有可依赖的法律依据以后，才启用无人值守的自动检查；启用前先改第 8 节的「自动访问」一项，写明做法和频率。本机运行、降低频率、不登录、不取字幕正文，都不作为取得平台许可的依据。首发不带自动检查脚本。
