# 简幕架构设计

2026年11月9日更新。

本文写代码怎么组织：模块怎么分、数据存成什么样、各部分之间怎么通信、怎么测、按什么顺序搭起来。产品是什么、各功能做到哪里算完成，见[产品需求说明（PRD）](product-prd.md)；分几个阶段做、发布前要满足哪些条件，见[简幕重构与双站首发方案](dual-site-launch-plan.md)（下称「方案」）。本文不重复产品行为，用到时写 PRD 的编号。

标注：本文写的结构都是首发待实现。2026-11-05 开发者本人取消独立实验，真实页面零轮；产品实机验证待做。首发指在 GitHub 公开发布可安装的版本（Releases 里的 zip），暂不上架 Chrome 应用商店（开发者本人 2026-11-07 定，PRD 第 5.3 节）。标「首发待验证」的要等第 10 步、第 11 步或实机核对的结论，括号里写等哪一项，汇总见第 14 节；标「初值」的数字实现时按实测再调；更新一到三只写首发留好的接缝。

## 1. 结论速览

1. 新代码写在新的公开仓库 `jianmu`，TypeScript 加一个自写的 esbuild 构建脚本。有测试的纯逻辑从现有代码逐模块移植，行为不变；后台路由、侧边栏、卡片、内容脚本、设置页、粗筛页按新结构重写，旧测试当行为规格。
2. 私有的旧仓库打一个参照标签，在上面录测试清单、性能基线，生成黄金样本。新仓库的移植步骤拿它对照，对不上就停。这些准备和公开骨架并行，不挡公开。
3. 统一视频身份 `{platform, videoId, segment?}`，所有键都由它生成。字幕、官方总结、标题简介都带内容指纹，概览、译文、问答都记下依据的是哪一份。
4. 站点适配层按能力工作。B 站接口的请求细节只出现在 B 站的读取实现、它的测试和模拟路由里，另有结构测试的地址放行表和清单的主机权限；B 站未登录时不读任何平台内容。请求签名和相关读取实现公开，第 6 步进公开仓库，第 7 步接进后台后进发布的安装包（方案第 4.4 节、本文第 6.5 节）。
5. 模式是一等概念：规则是纯函数，每个标签页的观看会话放在后台，播放计时在内容脚本，侧边栏和卡片只显示和发意图。
6. 花钱的入口都有来源标记和限额。内容脚本发来的任何信号都不能直接触发付费请求。读取视频数据先过首次启用确认，发给模型先过数据同意，这两道门和浏览器的站点授权分开管（第 9.4、10.2 节）。
7. 测试分两层跑：Node 里直接跑 `.ts` 的单元测试，无头 Chrome 里的页面测试和端到端测试。两站真实链接检查默认手动，见方案第 11.3 节。写代码时每轮跑一条 `npm run check`。YouTube 和首发新功能在后台服务搭好后就并行开工，提示词重写等 B 站对齐之后；B 站对齐和开发者本人切换日用，以及第 10 步「路线实机通过」，是发布准备定稿的进入条件，商标检索这类可提前做的发布准备从第 1 步起并行。

## 3. 总体思路和取舍

- **先有对照，再动代码。** 旧版的行为先录下来：单元测试清单、端到端每一步的断言、性能数字、纯函数在固定输入上的输出。
- **先搬有测试的纯逻辑，后写外壳。** AI 请求构造和解析、传输重试、分块合并、检索引用、字幕分段、并发、任务、清除闸门、粗筛逻辑是踩坑最多、测试最足的部分，按原样移植。外壳本来就要按模式重排，旧测试描述的行为照搬，写法重来。
- **一个 PR 只改一件事。** 移植、改身份、改行为、加功能各自成 PR。移植 PR 的黄金样本必须一致；改行为的 PR 逐条写明差异。出问题时撤回一个 PR 就回到上一步。

### 3.1 每一步都必须成立的不变量

任何一步破坏其中一条就回退。每条都要有对应测试；引入这条测试的那一步，退出前必须完成反向验证：故意改坏实现，确认测试会失败。

1. 不发意外网络请求：端到端模拟服务记下的意外请求为零。
2. 计费保护：取消后不重发；15 秒没人认领的任务自动收尾；限流重发不占自愈轮次；清除本机数据后拦下请求；service worker 被终止后不自动重发。
3. 数据同意先于任何 AI 请求，包括拉模型列表和测试连接。
4. 换视频不串台：迟到的回复不写到新视频上。
5. API 密钥默认只存于 `chrome.storage.session`。仅当用户在设置页明确勾选「在这台电脑上记住密钥」并保存，且扩展已成功把 `chrome.storage.local` 的访问限制为 `TRUSTED_CONTEXTS`，才把密钥和绑定的服务来源写入独立的本机记录；限制失败就拒绝写盘，已有的会话密钥继续可用。界面在勾选前说明本机副本未加密，以及删除后仍可能残留。两种模式都不向内容脚本、宿主网页、日志、报错、简幕导出的备份或浏览器同步暴露密钥。密钥只随请求发往绑定的、经用户授权的 HTTPS 来源。
6. 开放给网页的资源只有卡片页，只对 B 站；安装时只要 B 站的主机权限。
7. 清除闸门：两种清除范围各一个代数，先查代数再写，查和写在同一段里。清除闸门约束清除范围内的数据。站点退避状态不在清除范围内；晚到的限流信号只可更新退避状态，不能恢复用户资料、设置或启用确认。
8. 备份导入幂等，坏记录逐条跳过，不回滚整批。
9. 首次启用确认前不读取：后台不读视频信息和字幕，不查询、不观察标签页地址，不补注入；内容脚本不读页面数据、不插节点，卡片不插入（第 9.5、10.2 节）。

### 3.2 关键取舍

| 问题 | 选择 | 放弃的做法和理由 |
| --- | --- | --- |
| 数据库表首发建多少 | 只建首发用到的 7 个仓库；升级路径第 1 版就写好、测好 | 第 1 版就建齐 11 个仓库（含更新二才用的画面、删除标记）：为还没设计的功能预写形状，笔记本的导出格式还没核对，索引大概率要改 |
| 页面渲染怎么测 | 状态放在 `.ts` 的 signals store 里用 Node 测；渲染在无头 Chrome 里测 | linkedom 组件测试：多约 20 个包和一层构建，和 Preact 的配合也没实测 |
| 禁词名单放哪 | 公开仓库只做结构检查；带名字的禁词名单放私有侧 | 名单放公开仓库：名单本身就是要防的内容，等于写进公开仓库 |
| YouTube 字幕在哪读 | 契约同时允许后台直接读和经页面读，第 10 步按选定的路线实现一种；候选路线经页面读（第 6.4 节） | 先定成全部经标签页读：路线要到第 10 步才定 |
| 本窗口全部生成、稍后再看粗筛的循环 | 搬进后台批次服务，页面经端口连着。稍后再看粗筛在端口断开时停掉还没开始的条目；本窗口全部生成确认前的清点随端口断开停下，确认后的那一批照常跑完（第 8.5 节） | 留在页面里跑：确认后的那一批要在关掉侧边栏后跑完，更新一的标签页粗筛也要复用 |
| 提示词 | 移植阶段原样搬，只为端到端对齐；B 站对齐之后全部重写（第 8.2 节第 7 项），首发包里不留 Digest for Bilibili 原文的提示词 | 一开始就重写：代码移植的风险和提示词质量的风险混在一起，对照不出是谁的问题 |
| 新旧对齐和新功能 | 后台服务搭好后，YouTube、首发新功能和 B 站界面对齐三条线并行。三条线共用几份契约（设置结构、消息类型、任务、视频上下文、共用组件、端到端测试）；每份由哪一条线负责、改契约怎么合并、整合回归什么时候跑和跑什么，见方案第 4.5 节 | 严格串行（B 站对齐、日用几天后才接 YouTube）：最大的未知项落在关键路径最后 |

## 4. 新仓库 jianmu 怎么起步

### 4.1 进新仓库的和不进的

新仓库用全新历史。第一个提交只有骨架、文档和 LICENSE；之后每个移植 PR 从参照版本复制对应文件，改写后提交，旧提交历史不进来。公开时不能有哪些文件和内容，清单见方案第 5.2 节；这里只写代码上的约束：

- 与第 6.5 节边界冲突的代码和测试不搬，逐个文件的处理记在私有对照表里。B 站的读取实现进公开仓库，已登录路线用不到的代码不搬（第 6.5 节）。YouTube 实验代码也不搬。
- 只为防 Digest for Bilibili 旧功能回来的测试、旧存储迁移（密钥挪位、旧色板）不搬，新代码从来没有这些东西。
- 本机开发环境的配置文件放进 `.git/info/exclude`；提交规则等需要公开的约定并进 `AGENTS.md`。

新仓库的说明文件：`AGENTS.md` 删掉和 Digest for Bilibili 同步的一节，只写对所有贡献者都适用的开发约定，不写本机开发环境的配置；`notes/` 只放 PRD、方案、本文和按能力重写过的实机检查清单。

### 4.2 公开前和推送前的检查

完整检查项见方案第 5.2 节。这些检查控制的是公开什么，不代表已经取得平台许可。公开仓库的历史收不回，所以首次提交前在私有侧核对并处理不应公开的内容；此后每次推送前扫描工作区和全部提交历史，推送后另做远端复查。代码里落成三道：

1. **公开仓库 CI 里的结构检查**（`npm run check:public`）：不许有实验目录、`*.map`、`.env*`、`*.har`、实验导出的 JSON；`notes/` 走白名单。结构测试（第 5.2 节）另管依赖方向和主机名、路径样式字符串的位置。这一道不含任何带名字的名单。
2. **私有的推送前检查**：脚本和禁词名单都放在私有旧仓库，装成 `jianmu` 本机的推送前钩子，钩子只调用私有路径下的脚本。扫当前工作区和全部提交历史。名单按类别维护。
3. **不依赖本机的复查**：钩子只管开发者本人这台电脑。私有旧仓库里再放一个手动或定时触发的工作流，检出 `jianmu` 扫全部历史，有命中就提醒。仓库转公开前、每次发版前，各人工跑一次全历史扫描；发版前同时扫候选 zip 解压后的内容和 Releases 说明。

### 4.3 LICENSE 和致谢

LICENSE 保留哪些版权行、README 致谢怎么写，规则见 PRD 第 10、11 节。这里只写要做的事：第一个提交照搬现有 LICENSE 的 MIT 正文和三行版权；私有对照表记下每个新模块是「移植」还是「重写」，移植来的问答检索、字幕分段、AI 解析都会带着 Digest for Bilibili 的代码。最后一个移植模块也被重写时，按对照表改 README 致谢；那两行版权的去留见第 15 节。

### 4.4 旧测试的去向

旧代码有 91 个测试文件、1665 项（约 841 项直接调用模块，824 项靠 `vm` 跑整份脚本）、端到端主流程 30 步加 3 项收尾检查、生命周期 10 步。按文件定去向，先命中的为准：

1. 和第 6.5 节边界冲突的：不搬，换成新行为的测试（例如未登录报「需要登录」）；逐个文件的处理记在私有对照表里。B 站读取实现的旧测试跟着实现搬进公开仓库。
2. 守 Digest for Bilibili 旧功能不回来、旧数据迁移的：不搬，写明原因。例外：旧备份里带提示词时「忽略并告诉用户」保留，进旧格式读取器的测试。
3. 绑死旧文件布局的静态检查（脚本加载顺序、页面脚本和全局变量对应、打包脚本和死代码的正则）：不搬，换成构建产物检查和路由表断言。
4. 测纯函数、新代码还有的：一对一翻译，只改导入和视频身份。测跨模块行为、新代码还有的：先把用例标题抄成行为清单，再按新模块重写断言。
5. 拿不准的：搬。

守第 3.1 节不变量的测试，和守过一次线上问题的测试（测试或对应提交的说明里有「修」「防」「回归」），逐项列出，写明计划由哪个新测试接手。对照表放在私有旧仓库，每个文件一行，逐项条目另列。核对脚本分三段用，每段只查那时已经有的东西：

1. **准备阶段**（第 2 步）：旧测试分类完整，每个文件、每个逐项条目都有计划去向或不搬的理由。新测试这时还没写，不查它们在不在。
2. **每个移植 PR**（第 3 到 8 步）：对照表里指向本 PR 模块的条目，对应的新测试存在且通过；同一个 PR 把这些条目标成完成。
3. **最终对齐**（第 8 步退出前）：所有保留的条目都完成映射，没有停在计划里的条目。

### 5.2 依赖方向和结构测试

依赖只能往下：`pages`、`content`、`background` → `sites` → `platform` → `core`、`shared`。

- 后台经 `sites/services.ts` 取适配器。内容脚本 `content/<站>.ts` 只导入自己站的 `sites/<站>/page.ts` 和 `sites/rules.ts`，不导入任何站点的 `service.ts`（B 站的签名也只经它进后台包）；扩展页面只用 `sites/rules.ts`。契约文件例外：扩展页面可以只按类型导入 `sites/types.ts`，内容脚本可以导入 `sites/types.ts`、`sites/page-types.ts`。这样内容脚本包里不会带进签名和后台读取的代码。构建产物检查按 esbuild 产物里的源文件注释再核对一遍。
- `core` 同时被 `tsconfig.sw.json` 和 `tsconfig.pages.json` 检查，两边都要通过，保证纯逻辑不用某一端独有的接口。后台代码按 webworker 库检查，用了只有页面才有的接口直接报错。
- 注入 B 站和 YouTube 页面的标识（DOM id、class、CSS 自定义属性、主世界和隔离世界之间的页面事件名）一律以 `jianmu-` 开头，集中定义在 `shared/names.ts`。这些标识在别人的页面上公开可见，不加前缀容易和页面本身或其他扩展撞名。存储键和库名的前缀见第 7.3、7.4 节。

`tests/structure.test.ts` 读源码文本，守这几条：

1. 导入方向如上；`core` 里不出现 `chrome.`；`.ts` 不导入 `.tsx`。
2. 只扫 `src/`：两站的主机名和路径样式的字符串只许出现在 `src/sites/` 里。`src/core/ai/` 里模型服务的接口路径不算。`src/` 以外的清单模板、`tests/unit/sites/` 的地址解析测试、端到端模拟服务器、`notes/` 里按能力写的文档本来就要写，不算违规（方案第 5.2 节）。
3. `src/sites/` 下的注释只写用途。结构测试拦路径样式的字符串、外部链接、带下划线的字段名、常见写法的错误码和几种讲来历的说法，别的写法靠写的人和私有检查守；每个文件头注释不超过 3 行。
4. 单个源文件超过 500 行就失败，不再长出四千行的大文件。
5. `src/content/` 和 `src/sites/*/page.ts` 给注入的节点设 id、class、CSS 自定义属性，以及派发和监听页面事件时，只许用 `shared/names.ts` 的常量，不许写字面字符串；`names.ts` 里这几类常量都以 `jianmu-` 开头。
6. 两站读取的边界：`src/` 里不出现读 Cookie 的代码；`src/sites/` 不设 `Cookie`、`User-Agent`、`Referer`、`Origin` 这类表明身份的请求头。导入限制按规范化后的目标路径检查；页面模块和纯地址规则（`url.ts`、`page.ts`、`sites/rules.ts`）不发请求，不得直接或间接带入后台读取模块，服务注册表 `sites/services.ts` 只从各站的 `service.ts` 取服务；`url.ts`、`page.ts` 只许写播放页地址，内容脚本不发请求。B 站读取的请求出口固定为 `http.ts`，不经公共封装旁路。固定接口地址按放行表检查，加一条要改放行表；动态字幕地址由请求出口校验。结构检查（含导入关系的传递检查）和请求出口测试分别覆盖这些约束。

- 选轨的纯函数 `pickTrack(tracks, audioLang)`：原语言有可靠依据时，按原语言人工字幕、中文人工字幕、原语言自动字幕的顺序，其余排后。原语言无法确认时不设置原语言标记，先选中文人工字幕，再选其他人工字幕，最后是自动字幕，同一档里按固定的语言表（简体、繁体、其他中文写法、英文）排，显示实际语言和已确认的来源，默认选中的轨不说成原语言；只有一种人工字幕语言，不足以确认音频语言。它只用在拿得到完整轨列表的站，首发是 B 站。YouTube 不用它决定读哪一轨，默认读面板当前选中的原生轨（第 6.4 节）。
- 「读取当前画面」不进适配层：抓帧和编码是两站共用的 `content/shared/frame-capture.ts`，适配层只给 `findMainVideo()`，它分开报找到视频、正在播广告、找不到视频。内容脚本里要用视频元素的模块都经它取，截帧、播放计时、播放器指令、悬停图标和快捷键存笔记各自按结果处理（第 9.2、9.5 节）。它不属于画面功能，发行开关关闭时留在包里。
- 请求发出前、返回后、写缓存前各核对一次视频归属，在取字幕服务里做，不靠适配器自觉。B 站：一次读取开始时定下视频、分 P 的媒体版本和字幕轨，之后的请求都只用这组绑定；读取实现先核对返回的视频信息是不是请求的那个视频，对不上当作读取失败、不写入；字幕正文和官方总结本身不带可核对的视频身份，归属靠这组绑定保证，不逐份核对。迟到的结果只写回发起时的视频，不写到侧边栏当前的视频上。YouTube 另要核对导航代次和所选轨（第 6.4 节）。
- 第 3 到 9 步保留 `SiteService` 和可选的 `PageChannel` 契约，不为还没定的路线改形状。成功、空文件、串视频、限流这些行为测试可以先写，用替身跑；路线专属的桥和模拟第 10 步才加。

### 6.3 B 站实现什么

下面这些都在公开仓库里，边界见第 6.5 节。

- `url.ts`：现有代码里散在侧边栏、内容脚本、卡片、后台的十几份地址解析合并成一份。播放页、列表播放页、带语言前缀的同类页、av 号都认；追踪参数、起播时间不进身份。
- `service.ts`（入口，读取按能力拆文件）：视频信息、登录后的字幕轨和字幕正文、官方总结和附带的 AI 字幕、UP 主分段、稍后再看、限流识别和退避。每次新的读取操作开始前确认登录状态，只合并同时进行的登录检查，不跨独立读取操作复用已登录结论；登录确认失败或无法确认时不发内容请求，收到未登录信号时立即作废登录记录；登录检查同样受站点限速和退避约束，按需触发，不定时轮询；一次读取操作用一个读取环境，批量处理时每个条目算一次。读视频信息时分 P 超出范围报 `SEGMENT_OUT_OF_RANGE`，不再悄悄退回第 1 P（有意改变，界面提示见 PRD F01）。读视频信息时先核对返回的是不是请求的那个视频，对不上或看不出是哪个视频都当作 `MALFORMED`，不用这份结果，也不拿它判断付费（有意改变）。`MALFORMED` 一律标影响范围：只影响这一个视频，或这条读取路线这会儿整体读不了；批量处理据此跳过这一项或整批停下，不解析 `detail`（有意改变）。只有按已核实的响应规则能够确认属于非付费普通视频时，才读取字幕、官方总结和分段：付费和充电专属内容报 `UNPLAYABLE`；付费状态未知、必要字段缺失或格式不符时同样停止读取，同样报 `UNPLAYABLE`，`detail` 分别是 `paid` 和 `paid-unknown`，界面据此分开提示「付费内容不读」和「暂时无法确认可读范围」，不按免费处理。稍后再看采用同一规则。全部请求经站点限速和退避。字幕文件读取被限流也按限流处理，不再试下一条轨，也不重新列轨。第一次被拒时最多重新准备一次再试，仍被拒就退避（方案第 8 节第 1 项）。
- `sign.ts`：B 站接口要求的请求签名（第 6.5 节）。
- `page.ts`：主视频元素，`findMainVideo()` 在普通视频上报 `found` 或 `none`。B 站普通视频有没有要报 `ad` 的播放器广告、特殊播放器元素算哪种结果，第 11 步实测后定；实测之前不报 `ad`，取不到 `HTMLVideoElement` 时报 `none`；等页面框架激活（等页面加载完、服务端渲染的标记消失，再等 1.2 秒，照搬现有规则）；卡片插槽的几种位置；小窗避让；悬停图标挂载点（不能是直接包着视频的那一层）。

取字幕的顺序：用户导入过的字幕 → 平台字幕（按选轨顺序）→ 官方总结附带的 AI 字幕（注明来源）。最后一步只在视频没有字幕轨或字幕文件读取失败时走，用已经收到的那一份，不新发请求；被平台拒绝或限流时一律停下，不走这一步；这份字幕确认对观众可见之前默认关闭（首发待验证，第 14 节）。都没有时取字幕服务返回 `NEED_LOGIN`（未登录）或 `NO_CAPTIONS`；试过的字幕文件都是空的时返回 `EMPTY_CAPTION_FILE`。`NEED_LOGIN` 时只提示登录或导入字幕；`NO_CAPTIONS` 时概览服务按 PRD F05 改走只用官方总结、或只用标题和简介写结论的分支，后一支只在用户点击时走。

### 6.4 YouTube 实现什么（大部分首发待验证，第 10 步）

- `url.ts`：只认 `www.youtube.com/watch?v=`。视频编号只校验字符集 `[A-Za-z0-9_-]` 和长度上限 64，不写死位数：编号来自用户正在看的页面，校验太严会让功能整片失效，太松只多一条无害的键。Shorts、直播、嵌入页报不支持的页面。
- `service.ts`：读取路线在第 10 步定（第 12 节）。契约允许两种实现：后台直接读，或经 `PageChannel` 让内容脚本在页面里读。候选路线读观看页的文字稿面板，经 `PageChannel` 读（方案第 4.4 节）。硬性限制不放松：不读 Cookie 内容，不自行计算或构造平台用于校验请求访问权限的数据，不冒充其他客户端或设备，不复用、重放或伪造页面为自身请求取得的校验信息，不引起机器翻译字幕轨的请求，遇到限流或人机验证立即停下。读取时也不改变用户的播放器状态，用户点时间点引起的跳转和开始播放另算；不绕过访问限制。四种失败分开，各要有可辨的信号才报：空文件、没有字幕、被限流、需要登录。面板没打开是待用户操作；找不到入口可能是页面变了；加载中或空白不报空文件；其余报「暂时无法读取」。第 10 步按候选路线给 `SiteErrorCode` 加「待用户操作」和「暂时无法读取」两种结果。需要登录只在平台明确要求登录时报，明确信号是什么，第 10 步实测后定；只看到空文件时报空文件，提示登录或导入，不判定为需要登录。被限流或遇到人机验证立即停下，按站点全局退避；退避结束只放行用户的下一次操作，不自动续跑，不自动换路线。人机验证按 `RATE_LIMITED` 处理。
- 轨分三层，不混用：**当前可读轨**是页面现在读得到正文的那一轨；**可选轨**是在页面上选得到、能识别为原生轨的目标；**完整轨列表**是播放器给这位观众的全部人工轨和原语言自动轨。候选路线上 `listCaptionTracks` 只报前两层，不声称列全；完整轨列表是方案第 4.1 节第 2 条的验证参照，由验证者对照播放器核对，产品不遍历。结果按实际读到的显示语言和可确认的来源（PRD F02）。面板当前选的是翻译项或辨不清是不是翻译时不读，提示用户在 YouTube 面板里选原生轨；只是分不清人工或自动时记成未确认（第 7.2 节）。
- `PageChannel` 的能力分开：普通读请求只读面板已经显示的内容，自己打不开面板，也换不了语言。打开面板和切换面板语言是两条单独的指令，每条带一次性委托，只有用户在侧边栏里点对应按钮才能取得，绑定窗口、标签页、视频和这一次操作，用一次作废；换页、窗口失焦或撤权即作废，失败不重试。失焦按浏览器窗口算，用户点侧边栏不算。面板原已打开或用户中途接手时，简幕不动它；面板保持可见，读完不关，没有关闭面板的指令。取字幕服务、自动生成、批次和重试逻辑都拿不到这两条指令（第 10.2 节、PRD F02）。
- `page.ts`：用站内导航完成的页面事件加地址比对判断换了视频；地址和播放器数据里的视频编号都等于目标才算换好；播广告时 `findMainVideo()` 报 `ad`，不报 `none`。面板可能留着旧视频的内容，所以开始读、正文返回、写缓存前都核对视频、导航代次和所选轨，并要能证明面板内容已经更新；无法归属的结果一律丢弃。
- `main-bridge.ts`：按需生成，只在选定路线确实需要页面已有的数据时才有，做到最小、只读。只读当前视频、标题、频道、时长、简介、字幕轨列表；不碰密钥，不调 AI，不发跨站请求。和隔离世界之间用带随机标记的页面事件通信。主世界和网页共享执行环境，随机标记不能替代核对：隔离世界按不可信输入核对字段、大小和视频身份，后台不代取页面给出的任意地址。
- 路线专属的模拟路由用自造数据，测产品的成功和拒绝行为，第 10 步打通真实读取之后再做（第 11.3 节）。
- 中文对照用用户自己的模型翻译，不用平台的机器翻译字幕轨。
- 第二选择（用户自己开字幕时被动接收）：用户自己打开字幕后，扩展观察播放器自然收到的字幕响应。获选前还缺三项，任一项不成立就不选它，获选后再修订主世界桥、注入时机、清理和权限边界：
  - 架构和条款：要在页面主世界观察响应，超出上面「最小、只读」的约束，要单独审阅算不算干扰服务，验证原响应、错误、播放行为和其他扩展都不受影响。只处理当前视频的原生字幕，不改请求或响应，不拦翻译请求，不保存或转发平台返回的字幕地址。只收到用户选的一轨时，同样要面对方案第 4.1 节第 2 条。
  - 时机和信任边界：验证新开页面、站内导航、扩展晚启用三种情况。已经错过的响应不靠重放、刷新或替用户重开字幕补回。默认字幕关闭、记着自动翻译、只收到部分正文时各有明确结果。首次启用确认和站点授权都成立后才观察；隔离世界和后台核对来源、视频归属、字段和大小。撤权、停用、清除后，已打开的页面也要停止采集，注销脚本撤不回已经注入的代码。
  - 权限和披露：现有 `scripting` 加用户授予的 YouTube 观看页来源可能已够用，不预加 `webRequest`、`debugger`、`cookies` 或更广的主机权限。实际只能靠扩大权限或监控其他请求才能工作时，停在重新审阅。清单权限不变也要按实际行为更新首次启用说明和隐私政策，分别判断要不要重新确认本机读取和模型发送。

### 6.5 B 站适配层的边界

这里只写代码上的约束，公开时逐条核对的清单见方案第 5.2 节。这些约束控制的是公开什么、代码做什么，不代表已经取得平台许可。

- **放在哪：** B 站接口的请求地址、参数、签名、响应字段、限流识别只在 B 站的读取实现和它的测试里，模拟服务器里认得请求地址的模拟路由跟着它走，结构测试的地址放行表和清单的主机权限列出能请求的地址。其他模块只见契约的类型和错误码。
- **公开：** 请求签名和相关读取实现（入口 `service.ts`，签名 `sign.ts`）放在公开仓库的 `src/sites/bilibili/`，第 6 步进公开历史，第 7 步接进后台后进发布的安装包（方案第 4.4 节）；它们的单元测试、签名样本和认得请求地址的模拟路由跟着进公开仓库。不抄第三方接口文档，已登录路线用不到的代码不搬。
- **只有一份实现：** 发行构建、测试构建和开发构建读同一份代码，构建不替换入口，差别只在 `FEATURE_*` 开关（第 11.2 节）。
- **检查怎么配合：** 结构测试守源码（第 5.2 节第 6 条）。构建产物检查守产物：页面和内容脚本包里没有后台读取代码，产物里的源文件注释只有 `src/`、`prompts/` 和依赖包下的路径，不含测试替身。
- **边界：** 只读登录用户在 B 站页面上本来就能看到的内容，未登录不读任何平台内容（PRD F02）；不下载音频或视频，不碰付费内容，付费状态确认不了时也不读，保持低频，被平台拒绝或限流、遇到人机验证就停（方案第 8 节第 1 项）；请求只带浏览器自己的登录状态，代码不读 Cookie 值，也不读页面脚本环境；不生成设备标识，不冒充其他客户端或设备；不引用第三方接口文档，不带它们的文字和注释；平台返回的字幕地址不落盘（第 7.2 节）。
- **注释：** 只写用途，例如「B 站接口要求的请求签名」「读当前视频的字幕轨列表」。
- **测试：**
  - 单元测试给读取实现注入 `fetch` 替身，覆盖签名样本、未登录报 `NEED_LOGIN`、限流和被拒绝；后台服务用站点替身跑 B 站一侧的流程。
  - 页面测试和端到端测试跑 B 站的读取实现，请求发到本机模拟服务器，不访问真实平台；模拟服务器也能模拟未登录，断言界面提示「登录 B 站后可读取字幕，或导入字幕文件」。

## 7. 统一视频身份、存储和备份

### 7.1 视频身份

- 键唯一、能反解析：`bilibili:<BV 号>:p<N>`，第 1 P 也写 `p1`；`youtube:<编号>`。所有存储键、任务键、内存键都从 `videoKey()` 取；消息里传 `VideoRef`，不传零散的视频号和分 P。
- 不进身份：播放列表、合集、追踪参数、起播时间、语言前缀、av 号写法。
- B 站以分 P 号为准，内部媒体编号不进身份，作 `mediaVersion` 写进记录；读到的和记录里的不同，界面提示「这一 P 可能换过内容」。
- 频道身份 `channelKey()`：B 站是 UP 主，YouTube 是频道。按频道记住的模式用它，不用频道名。
- 链接只从身份生成（`canonicalUrl`），存着的链接字段不信、不导出。

### 7.2 字幕版本和派生结果

```ts
interface TranscriptRef { video: VideoKey; kind: CaptionKind; lang: string; fingerprint: string } // 每条「开始|时长|规范化正文」排序后取 SHA-256 前 16 位
type Basis =                                                              // 结果依据的是什么，四种来源
  | { source: "transcript"; transcript: TranscriptRef }
  | { source: "official-summary"; video: VideoKey; fingerprint: string }  // 官方总结正文规范化后取指纹
  | { source: "title-description"; video: VideoKey; fingerprint: string } // 标题加简介规范化后取指纹
  | { source: "legacy-unknown"; hint?: "official-summary" };              // 旧备份导入，依据未知；旧记录标过依据官方总结的留个提示
interface GenInfo { feature: FeatureId; promptVersion: string; model: string; effort: Effort } // effort 是实际生效的档位
type Derived =                                                            // 旧备份导入的记录不知道当时的生成配置，只有依据未知的可以缺 gen
  | { basis: Exclude<Basis, { source: "legacy-unknown" }>; gen: GenInfo }
  | { basis: Extract<Basis, { source: "legacy-unknown" }>; gen?: GenInfo };
```

- 带时效的字幕地址、凭据、抓取时间都不进指纹，字幕地址不进长期记录。平台返回的字幕地址也不进 `cache` 仓库，不落盘，换语言时重新列轨（首发待实现）。指纹持久化在记录里，service worker 被回收后照样能判断旧结果还能不能用。
- 结果绑定实际读到的内容：真实视频、语言、轨和正文版本，不按请求时想要的轨记。YouTube 上语言和来源以面板实际显示的为准，来源确认不了时记成未确认，不猜成人工或自动，第 10 步给 `CaptionKind` 加这一种。
- 界面按 `basis.source` 标注实际来源：基于字幕、基于官方总结、只依据标题和简介、未知（旧版）。只依据标题和简介的结论单独记这一种来源，不混成字幕概览（PRD F05）。
- 译文、概览、失败区间、问答、笔记摘录都带 `Derived`。依据变了（换了字幕，官方总结或简介改了）：只复用依据对得上的结果；对不上的不删不改，标「基于旧字幕」或「基于旧的官方总结」；补失败块只在依据相同时做。
- 笔记的原文、问答的引用原句存快照，字幕换了也能独立显示。
- 章节有版本指纹：全部章节的起始秒、标题和摘要规范化后取哈希。结论记下写它时读到的章节指纹，重点章节的起始秒列表放在结论里，和当前章节指纹对得上才显示（PRD F05）。补块改了章节，指纹就变了，旧重点不用删也不会显示；同一个时间点内容变了也不会被认错。

### 7.3 IndexedDB

库名 `jianmu`，首发版本 1。升级是按版本排好的步骤数组，`onupgradeneeded` 从旧版本逐级跑到新版本，以后加仓库就加一步，不改已有步骤。首发前就写一个「假想第 2 版」的升级测试（加一个仓库、加一个索引、旧记录不丢）。只有后台打开数据库；查询按索引取，不再全取出来在内存里过滤；写入一律经串行队列和清除闸门。

| 仓库 | 主键 | 索引 | 内容 |
| --- | --- | --- | --- |
| `notes` | `id` | `byVideo`、`byCreated` | 时间戳笔记，带 `kind`（首发只有 `note`）、`origin`、视频和频道快照、`Derived` |
| `overviews` | `videoKey` | `byUpdated` | 每个视频一份：一句话结论、章节、金句、失败和截断区间。章节部分和结论部分各带一份 `Derived`，并记下写入它的任务的创建时间（第 8.5 节）。结论部分另带可选的重点起始秒和章节指纹（第 7.2 节）。重新生成的进度放在 `draft` 部分，写完才换上（第 8.1 节） |
| `qa` | `id` | `byVideo`、`byCreated` | 问答，记下后不改 |
| `cache` | `videoKey` | `byTimestamp` | 视频信息、平台字幕（带 `TranscriptRef`）、官方总结、UP 主分段；30 天、60 条起步（初值，按性能测试定） |
| `translations` | 字幕版本加目标语言 | `byVideo` | 译文，带依据；不随字幕缓存的条数淘汰，上限按性能测试定 |
| `imports` | `videoKey` | — | 用户导入的字幕，一个视频一份，后导入的覆盖先导入的 |
| `channels` | `channelKey` | — | 频道 → 用户选过的模式 |

- 新建记录的 `id` 用 `crypto.randomUUID()` 加 `note_`、`qa_` 前缀；旧备份里的 `id` 原样保留，同一份旧备份导入两次不会重复。
- 有意改变：概览只存在 `overviews`，缓存里不再存副本，现有代码在缓存和长期概览之间来回同步的路径整个去掉；译文单独成仓库，付过费的译文不再随字幕缓存一起被挤掉。
- 侧边栏或设置页第一次打开时调用一次 `navigator.storage.persist()`，减少本机资料在存储压力下被浏览器清掉的机会。这个方法只在页面里有，service worker 里没有，所以不放在后台；方法不存在或返回 `false` 时照常运行，不提示用户。要不要改申请 `unlimitedStorage`（安装时有没有警告还没核实），放到更新二评估关键画面的存储时一起定。

### 7.4 chrome.storage 和 localStorage

| 键 | 区域 | 内容 |
| --- | --- | --- |
| `jianmu_settings` | local | 设置（不含密钥）：首次启用确认（确认时的说明版本和读取范围条目的指纹，第 10.2 节）、服务商、按功能的模型和推理强度、自动生成开关、站点启用、卡片开关、外观、数据同意（同意时的版本和说明指纹，第 9.4 节）、记住密钥开关（默认关） |
| `jianmu_model_caps` | local | 按「地址加模型」缓存的模型能力，含能否看图 |
| `jianmu_triage` | local | 稍后再看粗筛读到的列表快照和官方总结，30 天期限，过期按没有读过处理（首发待实现，PRD F15）。粗筛写的结论不在这里，跟着概览存在 `overviews`，和现有代码一样。更新一扩到三种来源时迁进 IndexedDB 的 `triage` 仓库，那是数据库第一次真实升级（预先计划的迁移，见第 13 节） |
| `jianmu_api_key` | session | 默认模式的密钥：`{key, origin}`，地址来源变了就丢弃 |
| `jianmu_api_key_local` | local | 记住模式的密钥：`{version, key, origin}`，独立于设置；只有用户选了记住才有，结构版本不对或缺来源就当作没填 |
| `jianmu_settings_revision` | local | 设置修订号（随机值）：密钥、密钥来源、记住开关、数据同意变了，或清除全部数据时换新，让过时的表单写不回去 |
| `jianmu_relaxed_params`、`jianmu_auto_ledger` | session | 参数放宽记忆（键带推理档位）；自动生成按「功能加视频键」记的尝试记录和限额计数（第 8.7 节） |
| `jianmu_site_backoff` | session | 站点的退避状态：只含站点、到期时间和连续命中次数，service worker 重启后还在，浏览器重启后清空。不是用户资料，两种清除都留着，避免清除后立即继续请求；晚到的限流信号只更新这里，不恢复用户资料、设置或启用确认 |
| `jianmu_watch_sessions` | session | 每个标签页的观看会话（第 9.1 节），含卡片的手动展开收起；同一标签页刷新同一个视频沿用原会话，标签页关闭时删 |
| `jianmu_appearance` | localStorage | 首帧外观缓存，`theme-boot` 同步读 |

- `storage.local` 和 `storage.session` 只给扩展页面和后台；读写设置一律经 `settings-store` 的锁。
- 用哪一份密钥只看记住开关，不按「哪边有值用哪边」挑。写本机记录前先把 `storage.local` 设成 `TRUSTED_CONTEXTS`，设不上就整次不存；后台每次醒来后的第一个事件也设一次。这个限制对 `local` 从 Chrome 140 起才可用，最低支持的 Chrome 116 只能限制 `session`，所以旧版本上选记住会明确报错，这次保存整次不生效，已有的会话密钥继续可用。访问限制只挡内容脚本，不是加密。
- 保存后的地址和密钥绑定的来源（域名和端口）对不上时，密钥从当前配置中移除，记住开关关掉，本机记录删除，换服务商和改自定义地址都走这条路。只改地址的路径不算来源变化，密钥保留；表单上切换、还没保存时，存储不动。
- 这里的删除和替换都是 `chrome.storage` 这一层的：接口读不到记录，不等于磁盘上已经擦除。现有 `chrome.storage` API 没有提供保证擦除底层残留的接口，删除或替换记录后，存储文件里仍可能残留旧密钥明文（Chrome 153 上实测，取消记住和清除全部之后仍能搜到）。卸载扩展时 Chrome 会删除扩展的本地数据，这也不代表安全擦除，不保证删除系统备份中的副本。对外不宣传可以彻底擦除。
- 新扩展第一次由用户重填密钥，不迁移旧扩展的明文密钥。
- 会话存储上限 10 MB，浏览器重启就清空，所以正在看的视频的模式重启后回到默认；频道偏好在数据库里，不受影响。

### 7.5 清除和备份范围：STORAGE_PLAN

`shared/storage-plan.ts` 写成 `as const satisfies Record<StoreName | StorageKey, Plan>`。新加仓库或键不登记，`tsc` 直接报错；清除、备份和测试都只读这张表。

| 数据 | 清除缓存 | 清除全部 | 进备份 |
| --- | --- | --- | --- |
| `notes`、`overviews`、`qa` | 留 | 清 | 是 |
| `translations`、`imports`、`channels` | 留 | 清 | 否 |
| `cache`、`jianmu_triage`、`jianmu_model_caps`、`jianmu_relaxed_params` | 清 | 清 | 否 |
| `jianmu_settings`、`jianmu_api_key`、`jianmu_api_key_local`、观看会话、自动生成记录 | 留 | 清 | 否 |
| 站点退避状态 | 留 | 留 | 否 |
| `jianmu_settings_revision` | 留 | 清除后写入新值 | 否 |
| `jianmu_appearance` | 留 | 各页面收到清除广播后按默认值重写 | 否 |

流程照旧：先取消全部 AI 任务，清服务内存，进闸门按表清除，广播 `data.cleared`。新增：侧边栏、卡片、粗筛页、设置页都听这个广播并清掉界面（现有代码只有粗筛页听）。清除全部会连带清掉首次启用确认，之后要重新确认。

密钥另有三个出口：「清除密钥」清会话和本机两处，记住开关跟着关；取消勾选立即删掉本机记录，本次会话仍可用，删除失败要明确报错，开关保持打开；保存后来源变化时按第 7.4 节移除。要删密钥时先换修订号再删，删到一半失败或后台被杀，之前打开的表单也写不回来。清除全部同样先换修订号，清除之前打开的表单保存时核对不过，写不回密钥，也写不回数据同意；修订号写不进去时不挡住清除，删完再写。这里的清和删都指接口读不到记录，磁盘上的残留见第 7.4 节。

导出界面按这张表列出不进备份的数据（译文、导入的字幕、频道偏好、设置、密钥、缓存），不称作「全部资料备份」。

### 7.6 备份

- 新格式 `{kind: "jianmu-backup", version: 1, exportedAt, notes, overviews, qa}`。数据库版本、记录版本、备份版本三套号各自递增，不共用常量。
- 重点章节是结论里的可选字段，不升备份版本，也不升数据库版本：新版导出再导入保留；缺字段按没有重点；坏的按生成时的规则过滤，概览保留。旧格式沿用原读取器和 `legacy-unknown`，不推断、不回填、不调模型。`draft` 不进备份。
- 导入先认格式：新格式走新读取器；Digest for Bilibili 和现有版本导出的旧格式（格式版本不超过 2 或没写）走 `core/backup/legacy-reader.ts`；版本更高的报「来自更新的版本」；都不是的报「不是简幕的备份」。
- 合并照旧：按 `id`，更新时间严格更大才覆盖，平局留本机，只写有变化的；逐条校验、逐条跳过，按类计数告诉用户。
- 有意改变：概览导入时过一遍和生成时相同的校验；视频号不合法的笔记跳过并计数（现在照常导入）；问答跳过的也计数。

旧格式一律按 B 站读，不猜成 YouTube：

| 旧内容 | 新内容 | 规则 |
| --- | --- | --- |
| 自定义提示词 | 丢弃 | 告诉用户提示词没有导入 |
| 笔记、问答的 BV 号和分 P | `video` | BV 号格式不对就跳过并计数；分 P 不合法按 1 |
| 笔记的时间点、正文、原文、标题、作者、时间 | `atSec`、`text`、`quote`、快照、时间 | 时间点不是有限非负数就跳过；正文 3000 字上限；缺更新时间用创建时间；`kind` 记 `note`，`origin` 记 `legacy`；链接、草稿、修订号这类能算出来或不再可信的字段丢弃 |
| 概览的视频标识 | `videoKey` | 先从 BV 号和分 P 推，再和旧记录键核对，不一致或都缺就跳过 |
| 概览的章节、金句 | 章节、金句 | 过新的校验 |
| 一句话结论的判断档位 | 四档，或保留旧判断 | 值得看完整视频 → 推荐看，可以跳过 → 可跳过，信息不足 → 信息不足。「看概览就够」原样记成旧判断，连同理由保留，不映射到新四档；用户重新生成结论后，这一项换成新档位。界面和粗筛怎么显示旧判断见 PRD F20。其他值只留结论文字。旧结论标过依据官方总结的，记进 `hint`，照旧标明 |
| 失败和截断区间；所有记录的依据 | 同名；`basis: {source: "legacy-unknown"}` | 只显示「这几段缺失」，补块要重新生成；依据显示「未知（旧版）」 |

测试样例照旧格式自己造，至少两份：现有版本风格（带问答，结论里有「看概览就够」和依据官方总结的）、Digest for Bilibili 风格（带提示词，笔记带修订号，概览没有结论）。真实备份只在本机跑一次回归，不进仓库。

## 8. AI 与任务层

### 8.1 分层

1. **方言**（`core/ai/provider/`）：按协议、地址域名、型号决定请求体和响应解析：推理档位、厂商私有参数（按域名放行）、图片部件写法、强制流式的拼回。
2. **传输**（`core/ai/transport.ts`）：照搬现有的超时、响应大小上限、三轮自愈、截断补齐、限流重发、不自动重试的错误、每次发出前重查同意。超时和输出预算随推理档位放宽。
3. **能力**（`core/ai/capabilities.ts`）：统一形状 `{canDisableThinking, efforts, imageInput, jsonSchema, maxOutput}`。能从服务商读到的就读，其余靠型号表、探测和放宽记忆。
4. **功能编排**（`background/services/`）：概览、结论、翻译、问答、划词解释、润色、画面解释，各一个服务。

失败时保留已完成部分：字幕先落库再进模型阶段，两站一样。概览每块完成就存；章节存完再写结论，结论失败只少结论；单独重写结论的入口是首发新增的（PRD F05）；停下时已完成的块照常保存，被停的块记成失败块；新功能沿用同一规则：每一步付过费的结果先存，再进下一步。

重新生成分开存「上一次的结果」和「这次的进度」。已有概览时，这次的章节和结论写进记录的 `draft` 部分，都写完才换上；中途停止或失败，不管停在分块还是写结论，界面和导出用的都是原来的章节、结论和重点，`draft` 留着，可以接着写结论，也可以放弃。没有旧概览的首次生成没有这一层，已完成的章节直接保存。现有代码只在分块阶段保护旧概览，章节写完就覆盖，这一点不照搬，是有意改变。

### 8.2 移植后一项一项加

每项一个 PR，黄金样本的差异只能来自这一项：

1. 原样移植三种协议、传输、能力、宽容解析和输出结构，请求体的黄金样本逐字节一致。
2. 消息内容改成部件数组（文本、图片），纯文本仍可写字符串，纯文本的样本不变。
3. 强制流式：按响应类型或正文开头识别，三种协议各自拼回普通响应；流中途的错误事件交给限流逻辑；设置页测试连接用同一个解析函数。首发不主动请求流式。不接受 JSON 输出格式参数的网关：报错点名这类参数时去掉重发，并记进放宽记忆。
4. 推理强度（第 8.3 节）、图片输入（第 8.4 节）各一个 PR。
5. 问答的用户消息改成「视频信息、字幕、问题」的顺序，字幕单独成块并打缓存标记；测试核对模板里问题在字幕之后。
6. Google 模型服务等其他服务商的 OpenAI 兼容端点（档位映射、关不掉时按最低档并标出、报错是数组形状的情况）；国内预设的默认模型名改成服务商现行的名称；报错统一成「原因、影响、下一步」（`core/errors.ts`）。
7. 提示词全部重写：现有六份（概览、一句话结论、翻译、问答、划词解释、笔记润色）和新增的画面解释，按速览、精读组织，学英语的提示词在更新三。和对应输出结构一起改，一句话结论的输出结构加重点章节，放在写结论这一步是因为这时才看得到合并后的全部章节，分块时每次只看到局部。本机校验放在 `core/ai/verdict`：按规范化的起始秒精确匹配现有章节，去重，最多三个，允许第 0 秒；缺字段、格式错、对不上只丢重点，有效结论照存，也不为补标重发。接受条件见 PRD F05；效果用开发者本人的密钥在几段固定样本上手动比，样本只存本机。等第 8 步 B 站对齐完成后再开工（最好第 9 步冒烟也已跑过）。完成时 `prompts/` 里没有沿用 Digest for Bilibili 原文的段落，用私有侧的比对脚本核对。

### 8.3 推理强度

- 设置 `featureEfforts: Record<FeatureId, "off" | "low" | "medium" | "high">`，新安装全是 `"off"`；换服务商时保留，按功能选的模型照旧清空。保留的是用户选的档位：换了服务或模型，方言层按新的服务和模型重新解析，请求参数按新结果发，设置页显示新的实际档位。
- 映射集中在方言层一张表：协议 × 域名 × 型号 × 档位 → 请求参数，同时回报实际生效的档位。做不到的档位退到最接近的一档，不退回「不发」；设置页按回报标出差别。
- 输出上限给思考留余量（关 0、低 2k、中 6k、高 16k）；硬超时关和低 120 秒、中 180 秒、高 300 秒，保活预算跟着算（都是初值）。同一功能内各块档位一致，免得破坏前缀缓存。

### 8.4 图片输入

- 三种协议的图片写法由 `parts.ts` 转换，图片放在文字前面。
- 画面分析单独一个功能槽，同一服务商、同一把密钥里选模型。能否看图：先查能力；查不到就在设置页选好模型后发一张 8×8 的图探测，按「地址加模型」缓存。被拒识别成专门的错误码，提示去设置页换模型，不进重试。
- 截图在内容脚本里缩放编码：长边 1456、JPEG 质量 0.85（初值，第 11 步按实际编码结果的读字情况定）。截图只用于这一次请求，不落盘，画面验证构建也一样。
- 第一次截帧之前，先完成覆盖读取当前单帧的首次启用确认（第 10.2 节）。第一次用画面验证构建向真实模型发截图之前，另外完成覆盖截图的数据同意（第 9.4 节）。
- 画面功能只在发行开关打开时进包（第 11.2 节）。进包时，方案第 8 节的 YouTube 条款审阅和 B 站实现条件自查均须覆盖当前单帧和相邻字幕的复制及发送给模型的行为。首发移除时，画面分析的模型选择、能力探测、消息路由、提示词、首次启用说明、同意说明和 README 的截图、演示 GIF 都随开关处理，逐项核对。

### 8.5 任务

- **两种键分开。** 互斥键管「同一时间只跑一个」，等价键管「能不能直接复用」。
  - 互斥键：`<kind>:<videoKey>`，翻译加目标语言。问答、划词解释、画面解释不设互斥键，同一视频可以同时问几个不同的问题，只按等价键合并连点。
  - 等价键：视频、依据版本（第 7.2 节的 `Basis`）、功能输入（问题、选区、目标语言、单独重写结论时的章节指纹、画面时间取到 0.5 秒档加截图内容的哈希、补块的区间；播放中同一档里截到不同的帧不算等价，连点时各解释各的帧）、生成配置（服务地址、模型、推理档位、提示词版本），规范化以后取哈希。
  - 依据还没定的时候：概览这类要先取到字幕才知道依据的任务，取字幕的阶段先按视频、功能输入和生成配置判断等价，取字幕服务对同一视频的在途请求本来就合并；依据定下以后再按完整的等价键核对，对不上的另起任务。
- **新请求怎么处理。** 等价键一致：接上在跑的任务，不另发一次。例如自动生成正在跑，用户再点「生成概览」，界面直接跟这个任务的进度。互斥键相同、等价键不同：用户发起的提示「已有任务在跑」，可以停掉旧的再发；自动生成和批次跳过这一条并标出原因，不排队。合并的只是等价的在途请求，重试和重新生成仍可能再次计费。
- **冻结生成配置。** 服务地址、模型、推理档位、提示词版本在任务创建时取定，跑的途中改设置不影响它，结果的 `GenInfo` 记的就是这一份。密钥按冻结的服务地址取，地址来源对不上就按密钥错误收尾，不把密钥发到别的地址。
- 首发种类：`overview`、`verdict`、`translate`、`qa`、`explain`、`frame-explain`、`triage-verdict`、`batch`。
- 每个任务记来源 `origin: "user" | "card" | "auto" | "batch"`（创建它的一方），另记订阅方：侧边栏、卡片、自动生成、批次，谁接上了这个任务谁就在里面。
- `triage-verdict`、`batch` 和来源是 `auto` 的任务列进「取消后仍占键」：已经发出的那次收尾前，不允许同一个互斥键再发。
- 认领、15 秒没认领自动收尾、两层保活、关掉发起页面照常跑完，照搬现有实现和测试。任务表只在内存里；service worker 被终止后不恢复、不重发，界面轮询发现任务没了就标成中断。
- **跟着页面走的任务：** 侧边栏手动发起的翻译、稍后再看粗筛，由后台服务跑，发起页面用 `runtime.connect` 连着。端口断开只退订这一个页面：所有订阅方都是跟着页面走的、并且都断开了，才停掉还没开始的批次或条目，已经发出的收尾；还有别的页面或自动任务订阅着这个等价请求，就照常跑完。这保住现有「关页即停、不替用户花钱」的费用语义。本窗口全部生成只有确认前的清点跟着页面走。
- **不跟页面走的任务：** 概览、问答、来源是 `auto` 的翻译，以及用户确认过的本窗口全部生成，关面板照常跑完并保存；重开侧边栏时接上还在跑的条目，照样可以全部停止。这和现有行为一致（PRD F13）。
- **写同一条记录：** 概览和单独重写结论都写 `overviews` 里同一个视频的记录，按字段合并：概览任务写章节部分（章节、金句、失败和截断区间）和它顺带生成的结论，单独重写结论的任务只写结论部分。每部分记着写入它的任务的创建时间。写入在串行队列里先读出现有记录再比较，较早创建的任务不覆盖较晚创建的任务已经写下的部分：概览跑到一半时用户另外重写了结论，概览收尾时不会把新结论换回旧的。重点章节属于结论部分，和结论一起写。单独重写结论落库前再核对一次章节指纹，对不上就不写入；成功返回零个重点时清掉上一版；失败或被停止时原结论和原重点不动。

### 8.6 本窗口全部生成和粗筛

批次服务在 `background/services/batch.ts`。首发有两种来源，走法不同：

- 「稍后再看」：来源 → 清点 → 读官方材料（不花钱）→ 用户确认 → 写结论。第一步的节奏照旧（间隔 1.5 秒、被限流即停、连续两个要登录即停）。
- 「当前窗口（只生成概览）」：来源 → 本机清点 → 用户确认 → 逐个读取 → 生成概览。确认前只看标签页的地址和标题，查本机已有的概览和任务状态，不向平台读取任何内容。确认后只处理合格条目，读平台沿用粗筛的节奏和停止规则：逐个读，条目之间有间隔，被限流就停，不吞成「没有概览」。

清点用 `sites/rules.ts` 认两站地址；YouTube 标签页在启用后才看得到。看得到的 YouTube 标签页只在本机清点、显示已有结果，待生成的标「需逐个打开」，不进本批任务数和费用；批次不读 YouTube 字幕，也拿不到打开面板和换语言的指令（第 6.4 节、PRD F13）。用户之后自己切到那一页，走单视频入口。「切过去」只指用户自己切，扩展不替用户切标签页，不替用户刷新标签页，也不为批处理另开读取路线。更新一的标签页粗筛和分 P、合集粗筛是再加来源，不默认恢复对后台 YouTube 标签页的读取。

### 8.7 打开 B 站视频就生成概览

- 首发只对 B 站生效（PRD F10）。YouTube 视频不进这条路径：打开视频、切到前台或打开侧边栏，都不为自动概览或自动翻译取字幕，已有缓存或导入字幕也一样；缺材料不发模型请求，不记尝试。这条站点限制放在下面的闸门之前，概览和翻译同样适用。
- 由后台自己观察：`tabs.onActivated`、`tabs.onUpdated` 看活动标签页的地址（有主机权限才看得到），`windows.onFocusChanged` 看哪个 Chrome 窗口获得焦点，用 `sites/rules.ts` 认视频。「打开视频」指获得焦点的窗口里的活动视频标签页，后台打开的标签页第一次真正进入前台时才算（PRD F10）。只看标签页是不是活动的不够：没有焦点的窗口里也有活动标签页。焦点离开 Chrome 时不触发，切回来时按当时的前台标签页再判断一次。视频身份只从标签页地址解析，不信内容脚本。
- 先过四道共用的闸门：站点（已确认启用简幕，这个站已启用）、同意（版本和说明指纹都对得上）、配置（开关开着，模型配置齐）、额度（不在额度用完的暂停里，自动任务的限额还有余量）。
- 再按功能分别判断，概览和翻译互不挡：
  - 概览：这个视频没有任何概览记录（基于旧字幕的、不完整的都算有）；有可用的字幕或 B 站官方总结（两样都没有不发请求，标出原因，PRD F05）；本次浏览器会话里没为这个视频自动试过概览。旧字幕或不完整的概览不自动重做，由用户点重新生成或补块（PRD F05）。
  - 翻译：外文视频；当前字幕版本还没有目标语言的译文；本次浏览器会话里没为这个视频自动试过翻译。已有概览、还没有译文的外文视频照样自动翻译。
- 尝试记录按「功能加视频键」记在 `jianmu_auto_ledger`，模型请求真正发出时才记，发出后失败也算试过，不静默重试。
- 发请求前重新核对：触发时的窗口仍有焦点，那个标签页仍是它的活动标签页，标签页地址解析出的视频仍是触发时的视频。读字幕这类步骤是异步的，所以在真正调模型之前再核对一次；任何一样变了就放弃这次，不记尝试，等它下次进入前台再判断。
- 自动任务单独一道闸门：同时只跑 1 个，滑动 10 分钟最多 20 个（初值）。服务商报额度用完或密钥错误，停掉自动生成，侧边栏顶上一行提示；用户手动成功一次或重开开关后恢复。

## 9. 界面与模式状态

### 9.1 模式状态放在哪一层

| 层 | 内容 | 放在哪 |
| --- | --- | --- |
| 规则 | `decideMode`、播放累计 | `core/mode/`，纯函数 |
| 频道偏好 | 频道 → 用户选过的模式 | 数据库 `channels`，经后台读写，设置页可清除 |
| 观看会话 | 每个标签页：视频、模式、模式来源、是否已自动切过、累计播放秒数、会话开始时间、卡片手动覆盖 | 后台 `sessions.ts`，写进 `jianmu_watch_sessions` |
| 视图 | 显示哪些区块、「已切到精读」提示和它的计时、展开了哪一章、问答抽屉、草稿和焦点 | 侧边栏、卡片各自 |

`decideMode` 的输入是时长、频道偏好、本次手动选择、累计播放秒数、当前模式和来源、这次是否已自动切过；输出模式（`skim`、`study`，`english` 在更新三才可选）和来源（手动、频道、短视频、默认、自动）。优先级和自动切换的规则照 PRD 第 6 节写成它的测试表。侧边栏和卡片只读会话、发意图（`session.setMode`），自己不算模式。开问答抽屉、输入、发送、点引用都不发 `session.setMode`；只有主动点模式切换才发，才记频道。

问答抽屉和模式是两层状态：模式变了，抽屉、草稿、焦点和在途回答都不动。撤销提示只在看得见、点得到时计时，抽屉或优先级更高的提示挡住、标签页不在前台时暂停。

观看会话按标签页记。同一标签页刷新同一个视频算同一次观看：标签页地址解析出的视频键没变，就沿用原会话，模式、模式来源、「已自动切过」、累计播放秒数和会话开始时间都保留。刷新后内容脚本报 `playback.info` 时，后台在回复里带上会话里的累计秒数，内容脚本从这个数接着累计；刷新前最后一次上报之后的那不到 10 秒不计（第 9.2 节）。换了视频或关了标签页才开新会话。

### 9.2 播放计时

- 计时在内容脚本（`play-reporter.ts`）：只有它拿得到视频元素，侧边栏关着也能计。规则在 `core/mode/play-clock.ts`，内容脚本只喂事件。
- 视频元素一律经 `findMainVideo()` 取。报 `found`，并且在播、没在拖动、已有画面时，累加两次采样之间的真实经过时间，单次最多 1.5 秒；报 `ad` 或 `none` 时不计；播放位置跳动超出预期 2 秒按拖动处理，不计。暂停不清零，倍速按真实时间算。
- 每累计 10 秒报一次 `playback.milestone`，带累计秒数。后台核对后写进会话；满 60 秒时调 `decideMode`，变了就写会话并广播 `session.changed`。后台在回复里告诉内容脚本还要不要接着报：已自动切过，或这次观看里手动选过模式，就停报。
- 时长和频道：内容脚本在 `findMainVideo()` 报 `found` 之后，从页面上已有的视频元素和页面数据里取（读得到时），经 `playback.info` 报给后台，侧边栏关着也一样，不另发平台请求。报 `ad` 时不发：广告的时长不能当成视频时长，这条消息每个视频只发一条。后台只用它定模式，不作任何付费请求的依据；侧边栏打开后以适配层读到的视频信息为准。第 10 步如果发现要另发请求，同步改方案第 8 节第 2 项。

### 9.3 侧边栏

- `app.tsx`：首次启用确认（没确认时只显示说明和「启用简幕」按钮，不读任何视频数据，第 10.2 节）、视频信息、模式切换、一行提示（连接问题、「已切到精读」、同意说明更新了）、同意闸门、当前视图。
- `skim/`：结论卡、章节列表（每章展开这一段的字幕，标出重点章节）、B 站官方总结和 UP 主分段、「生成概览」和进度。YouTube 上还没读到字幕时，先显示读取提示和按钮，读到以后显示实际轨道，再给「生成概览」（PRD F02）。
- `study/`：跟随播放的字幕（当前句高亮、回到当前句、搜索、双语）、当前章节、划词解释浮层、存笔记、「解释当前画面」按钮。
- `qa/`：问答抽屉，速览和精读共用，挂在 `app.tsx` 下面，切模式时不卸载。底部的入口只打开抽屉，用户提交才发请求。
- `notes/`、`batch/`：本视频和全部笔记、编辑、导出；本窗口全部生成。
- 共用：`video-context.ts` 定死当前视频和票据，所有异步回来先 `isCurrent(ref)`，现有代码里散在九处的票据规则收在这里；`task-follow.ts` 接管别处发起的任务，侧边栏和卡片共用；字幕视图可以开多份（主列表、章节里的片段各一份）。
- 状态都在 `.ts` 的 signals store 里，组件只渲染；Node 里测 store，无头 Chrome 里测渲染。

### 9.4 播放页卡片和其他页面

- **卡片**（只 B 站）：Preact 页面，内容脚本用 iframe 插入，和侧边栏共用结论、章节组件，单独打包。提问入口只在侧边栏。展开收起读本标签页的会话（`session.get` 只回卡片所在的标签页）；手动展开收起经 `card.setOverride` 记进会话，换视频即失效。插入位置、高度上报、父页面来源核对、开关、限频和令牌照旧；收起时不读数据；后台打开的标签页第一次到前台才读（首发待实现，PRD F14）；首次启用确认前不插入。
- **粗筛页：** 逻辑在 `core/triage/`，页面重写，四档分组，说明文字按 PRD F15 改正。
- **设置页：** 启用简幕（读取说明和启用状态）、AI 服务（服务商、密钥、拉模型、测试连接、按功能选模型和推理强度、画面分析模型、数据说明和同意）、站点、自动生成开关、模式（清除记住的频道）、外观、播放页卡片、学习资料（备份、清除）、关于、粗筛入口。启用简幕、站点授权、数据同意是三件事，各管各的：启用只管扩展在本机读不读视频数据（第 10.2 节），站点授权是浏览器的主机权限（第 10.4 节），数据同意只管发给模型服务的内容。
- **记住密钥：** 设置结构和读写锁移植完以后，用独立的功能 PR 加入（第 12 节第 5a 步）。勾选框默认不勾，勾选前写明本机副本未加密、取消记住后本次会话仍可用、哪些操作会移除密钥记录，以及删除后仍可能残留、卸载不等于安全擦除；担心泄露可到服务商后台撤销密钥，共用电脑不要开。取消记住后的提示、清除确认和成功提示用同样的说法，中英文同步。只勾选不写盘，要点保存，而且访问限制设成功才写。这是单独的选择，不沿用 AI 发送的数据同意。设置页保存时带上表单打开时的修订号，在锁里核对，对不上就整次不存并重新载入；即改即存要比对写之前的修订号，别的页面改过也重新载入。侧边栏和卡片监听本机记录，只换密钥时不用刷新就更新状态。
- **同意闸门的机制：** `core/consent.ts` 是一张按版本排的表，每个版本记下相对上一版新增或扩大了什么：数据类别、使用目的、接收方、发送的触发方式或范围。说明的实质内容就是这张表里的条目，不含措辞；对这些条目算一个指纹。同意时把版本和指纹都存下，两样都和当前一致才放行，否则拦下全部 AI 请求。只改文字不动条目，版本和指纹都不变，不用重新同意。条目变了却忘了升版，指纹对不上照样拦下；另有一份「版本 → 指纹」的测试快照，改了条目没升版测试就失败。开发期间也一样：开发构建里已经有人同意过的说明，之后扩大了范围就升版，旧同意失效，不因为还没发布就沿用。没存过的显示完整说明；存过旧版本的只列之后新增的内容，不把同意问题报成密钥错误。什么算实质变化见 PRD 第 9.2 节，版本号怎么定见方案第 7.3 节。

### 9.5 内容脚本

- **等启用确认：** 加载后先向后台问一次启用状态。没确认时只挂一个听 `activation.changed` 的监听，不读页面数据、不插节点、不计播放时间；确认后才往下走（第 10.2 节）。
- **等页面激活：** 先挂监听，不碰 DOM；`whenPageReady` 之后才插节点，避免打断评论区、顶栏、网页全屏。
- **悬停图标：** 浮层的 id、class 和样式变量按第 5.2 节以 `jianmu-` 开头。一个浮层两个图标：存笔记、解释当前画面（后者受构建开关 `FEATURE_FRAME_EXPLAIN` 控制，第 11.2 节）。显隐跟着适配器的控制栏信号，拿不到信号时退成鼠标在播放器上移动后显示 3 秒。显隐用 `visibility` 加 `pointer-events`，在可见状态下记录注入时的样子，防点击劫持的核对才有意义；点击只认真实点击，再核对透明度、可见性、尺寸。保存反馈用图标状态加一句短提示。图标的显隐不跟广告状态联动；点击和按快捷键时按 `findMainVideo()` 的结果处理，报 `ad` 时不存笔记、不解释画面，只提示正在播广告。
- **截帧：** 找主视频，`findMainVideo()` 报 `none` 按没找到视频拒绝，报 `ad` 按正在播广告拒绝；检查画面已就绪；视频元素挂了 `mediaKeys` 就按加密播放拒绝（首选信号；会不会误判普通视频、要不要再看 `encrypted` 事件，首发待验证，第 11 步），保护状态无法可靠判断时同样拒绝，由扩展在截取前主动识别，不靠截出来是不是黑帧来判断；标签页在前台；播放中用 `requestVideoFrameCallback` 等下一帧，等到后再看一次 `findMainVideo()`，报 `ad` 按正在播广告拒绝；画到 `OffscreenCanvas`，缩放，编 JPEG，转 data URL；回传画面、尺寸、播放时间和视频身份。失败分开报：没找到视频、画面没加载好、受版权保护、画布被污染、不在前台、正在播广告、视频已换。不用整页截图的接口。画面验证构建和发行构建跑同一份内容脚本代码，拒绝路径的测试分工见第 11.3 节。
- **播放器指令：** `player.getState`、`player.seek`、`player.captureFrame`；更新三加区间播放和暂停。所有指令带视频身份，对不上回 `VIDEO_CHANGED`。涉及播放时间、跳转、时间戳笔记和截帧时，另行确认主视频元素已对应当前视频；无法确认时拒绝。不得仅以地址一致代替播放器身份核对。视频元素一律经 `findMainVideo()` 取：报 `ad` 时 `player.getState` 说明正在播广告，不带播放时间，字幕高亮停在原处；`player.seek` 拒绝并提示正在播广告，不动播放器，不跳过广告；报 `none` 按没找到视频回。
- **扩展重载后收场**照搬现有规则。安装、更新后补注入（`background/reinject.ts`）：往已开的 B 站视频页和已启用的 YouTube 观看页注入一次。补注入要先按地址查标签页，所以首次启用确认前不做；用户点「启用简幕」时，对已开的视频页补注入一次。内容脚本按扩展实例做防重复注入，旧实例发现扩展上下文失效就自己撤掉；补不上的页面提示刷新。

```ts
  beforeEnable?: true;                       // 首次启用确认前也放行；不写就要求已确认（第 10.2 节）
  handler: (req: Api[K]["req"], ctx: SenderCtx) => Promise<Result<Api[K]["res"]>>;
}
export const ROUTES: { [K in keyof Api]: Route<K> } = { /* … */ };   // 漏一条路由，tsc 报错
```

- 一张路由表取代现有后台里的 32 个分支。放行测试直接遍历 `ROUTES` 逐条断言，外加「不在表里的消息一律拒」。
- 发送方分类照搬现有规则：地址以扩展前缀开头的是扩展页面；嵌在网页标签页里的扩展框架一律按卡片；自己占一个标签页的再按路径比对；其余带标签页的按地址分站点算内容脚本，站点在启用闸门之后才解析；都不是就拒。
- 广播是一个判别联合：`task.changed`、`overview.preview`、`overview.updated`、`notes.changed`、`session.changed`、`data.cleared`、`panel.follow`、`appearance.changed`、`activation.changed`。各页面按任务号、视频键或标签页号过滤。

- 内容脚本发来的消息，视频身份一律从发送方标签页的地址重新解析，消息里的视频只作提示；地址在启用闸门之后才读。
- 页面主世界发不了扩展消息，只和隔离世界说话，按不可信输入处理。

- 后台从不代取页面传来的任意地址。
- 上表只限制能力，不是密钥的边界：卡片虽然嵌在网页里，仍是受信的扩展页面，能读到密钥，也会在存储变化里收到密钥。卡片靠严格的 CSP 和不渲染未转义内容来守，存储事件的内容不转发、不写日志。
- **启用闸门：** 首次启用确认记在 `jianmu_settings` 里（确认时的说明版本和读取范围条目的指纹）。确认前，路由表里没标 `beforeEnable` 的路由一律回 `NOT_ENABLED`，后台不读视频信息、字幕、官方总结和各种列表，也不观察标签页发起自动生成。确认前允许读取启用状态、确认启用、读取外观、打开设置页和侧边栏；另允许设置页清除本机数据、导出已有资料备份及回收不再需要的授权。这三项不得触发平台或模型请求，也不得查询、观察标签页地址。说明写清 PRD F22 列出的读取范围和本机缓存的用途，显示在侧边栏和设置页，用户在那里点「启用简幕」才写入并广播 `activation.changed`；只有这两个扩展页面能确认，卡片和内容脚本不能。不必每个视频确认一次。启用和浏览器的站点授权、向模型发送内容的同意分开存、分开判断：授权了站点不等于启用，启用了也不等于同意发给模型。说明的读取范围有实质变化时，按第 9.4 节同一套规则（版本加指纹，另有快照测试）升版、重新确认。已确认过的人，版本或指纹和当前不一致就按未确认处理，闸门照常生效，说明只列之后新增的内容，点「启用简幕」后恢复。当前单帧这一条只在 `FEATURE_FRAME_EXPLAIN` 打开的构建里进说明和指纹，开关关着的构建停在不含这一条的版本；「版本 → 指纹」快照两种开关状态各一份，同意表里的截图条目同样处理。
- **YouTube 代操作：** 打开文字稿面板和切换面板语言只接受侧边栏里用户点击发来的请求，后台按第 6.4 节的一次性委托核对后转给内容脚本。内容脚本、卡片、网页都发不起这两条指令，后台服务也不能自己发。
- **截图核对：** 截图一律由后台向那个标签页要。回来的数据先核对：前缀必须是 `data:image/jpeg;base64,`，不超过 4 MB，视频身份和发送方标签页一致；不符就拒，不发给模型。
- **悬停图标解释画面的结果：** 显示在侧边栏。Chrome 官方支持由内容脚本里的真实点击打开侧边栏；打开侧边栏要在用户手势还有效时调用，所以后台收到 `frame.explainHere` 后第一件事就是打开侧边栏，前面不夹任何异步等待，之后才截帧、调模型。待实机验证的只是这条具体调用链（点击经消息到后台再打开）能不能走通；走不通时在页面浮层里提示「结果在侧边栏，点简幕图标查看」，结果留在会话里等侧边栏打开。

### 10.3 限频和防伪造

| 入口 | 规则 |
| --- | --- |
| 卡片生成概览 | 每分钟 3 次；只认真实点击；登记过的任务号用一次就删（照搬） |
| 播放页笔记润色 | 每分钟 6 次；超出只存原文（照搬） |
| 悬停图标解释画面 | 每标签页每分钟 6 次（初值）；真实点击加样子核对；截图核对 |
| `playback.info` | 每个视频一条，换视频才发下一条；视频必须等于发送方标签页地址上的视频；时长、频道编号过一遍形状和大小核对，只用来定模式 |
| `playback.milestone` | 每标签页 10 秒最多 1 条；累计秒数只增不减，且不超过会话开始以来的真实经过时间加 2 秒；视频必须等于发送方标签页地址上的视频 |
| 打开视频自动生成 | 第 8.7 节 |
| YouTube 代开面板、代换语言 | 用户点一次发一次；委托用一次作废，换页、窗口失焦、撤权即作废；失败不重试（第 6.4 节） |

播放进度上报只能改界面模式，不能触发任何付费请求。以后凡是由页面信号引出的付费请求（更新二的精读自动准备候选），只认后台自己的会话状态，并按「视频加依据」去重、套全局上限。

### 10.4 权限

- 必需权限只有 `sidePanel`、`storage`、`scripting` 和 B 站的主机；YouTube 和 AI 地址都走可选主机权限，运行时按来源逐个申请。具体清单、用途和不申请哪些权限见方案第 7.1 节。
- B 站内容脚本静态声明。YouTube 在用户启用的那次点击里申请，拿到后动态注册隔离世界一份脚本；选定路线需要时再加主世界一份（按需生成；首发待验证，第 10 步）。脚本路径取自 `shared/names.ts`，注册几份按第 10 步选定的路线定。同步注册的时机：`runtime.onInstalled` 的安装和更新两个分支都走，更新后不假定原来的注册还在，按当前授权重新注册；`runtime.onStartup`；权限增减时。停用或撤权时注销，并通知已开的 YouTube 标签页撤界面、停读取（注销不会撤掉已注入的脚本），没用掉的代操作委托一并作废。
- `grants.ts` 取代现有的权限回收：保留集合 = 清单主机 ∪ 内容脚本的匹配规则 ∪ 已启用站点的来源 ∪ 当前 AI 地址的来源。按主机权限的匹配范围判断保留关系，路径不参与比较；匹配规则未指定端口或端口为 `*` 时覆盖所有端口。候选授权与任一保留规则之间，只要一方覆盖另一方，就不回收；无法识别、不能确认可安全回收的规则也不回收，以避免误撤仍需保留的权限。因此，当前 AI 地址对应的规则未指定端口时，同一主机带端口的授权也保留。其余可选授权一条一条收，一条失败记日志、不连累别的。测试替身的 `getAll()` 按实测形状返回，带上内容脚本的匹配规则。现有回收的问题见方案第 2.1 节；修好并在实机上验证后，隐私政策才写回收的说明，边界见方案第 7.2 节。

4. 读取实现首次推到公开分支或出现在公开 PR 之前，按实际行为补完方案第 8 节的 YouTube 部分并审阅。
5. 路线实机通过：端到端 YouTube 步骤通过，约 12 个真实视频按方案第 4.4 节的实机清单实机通过；用户自己开面板、简幕代开、简幕代换语言分开验证。

代开或代换语言不通过时，按方案第 4.4 节的失败层级退，不算换候选。要换候选，回到「选定候选路线」重新筛选，开发者本人重新审阅条款说明，新候选重新取得实机证据。一轮被叫停后怎么重开、这一轮怎么记，见方案第 4.4 节的实机清单。YouTube 找不到满足条件的路线，两站都不发布。

**第 10 步的实机清单**以方案第 4.4 节为准，样本、账号、参照、结果、操作、身份、停止和记录都写在那里。

**第 11 步解释当前画面的顺序。**

1. 先验证截帧：第一次截帧之前，先完成覆盖「读取当前单帧，用于解释画面」的首次启用确认（PRD F22）。然后用画面验证构建确认两站普通视频（不含番剧、电影、付费内容）能唯一找到主视频，读出和屏幕一致的当前帧，并在截取前主动识别加密播放。保护状态无法可靠判断时拒绝。对照用产品内容脚本的输出，不为对照新增主世界脚本；截图不落盘。
2. 这些过了，再接模型和两个用户入口。第一次用画面验证构建向真实模型发截图之前，先完成覆盖截图的数据同意（第 9.4 节）。
3. 量化标准：按方案第 4.5 节的判定表逐项核对。
4. 拒绝条件：逐项核对 PRD F11 用法一，包括找不到视频、加密播放、正在播广告、标签页不在前台、视频已换、画面未就绪和模型不能看图，找不到视频和正在播广告分开提示。
5. 全部通过才打开发行开关，并在最终候选包上回归（第 12 步）。画面验证失败或缺少关键证据，首发移除全部画面功能。

## 13. 更新一到三的落点

怎么判断首发的接缝留对了：首发后加一个功能，如果要做计划外的改动（改已有记录的形状、迁移本机数据、重排已有模块），就说明接缝没留对。表里已经列出的两项是预先计划的：`jianmu_triage` 迁进数据库的 `triage` 仓库、概览记录加画面要点字段。首发不为它们预建仓库或字段（第 3.2 节：不为还没设计的功能预写形状），升级步骤和测试跟着那次更新写。

每项要不要升同意版本、重新同意，按 PRD 第 9.2 节和方案第 7.3、10 节判断；本机读取或保存的内容变了（例如笔记里插关键画面要在本机存截图），同时按 PRD F22 改首次启用说明。本表只写代码上的接缝，不另下结论。
